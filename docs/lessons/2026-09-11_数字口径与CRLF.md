# 数字没有口径 / CRLF 让对拍与门禁失真
复发次数: 16
作用域: 全局
最近复发: 2026-10-07
现象：两个工具数同一文件行数差几十；逐字节对拍永远不等；`git hash-object` 相等**且** `git diff` 为空却仍掩盖 EOL 差异；`git stash` 后 Vite 拒绝构建；`Get-Content` 读中文日志 GBK 吞行（"新增 6 条"实为"新增 0"）。**2026-10-07 母版仓复发**：`Get-Content test/route-cli.test.mjs`（无 BOM 的 UTF-8）报 **618** 行，而 `[IO.File]::ReadAllLines($p,[Text.Encoding]::UTF8)` 与字节计数（LF 653 / CR 0）都是 **653** —— 差 35 行；仓里所有 `.ps1` 读法都是对的，错的只是**人顺手敲的那条命令**（收工前量行数用的就是它）。**2026-10-07 同一天第二次，换了个面（卡面行数）**：量 `playbook/4-2-代码审查.md` 的卡面行数（硬上限 150 行）时 `(Get-Content $f).Count` 报 **90** 行、`Get-Content -Raw` 报 14362 字符，而 `[IO.File]::ReadAllLines(UTF8)` 与 LF 字节计数都是 **150 行 / 11322 字符**——一次差 60 行，差点据此把台账里"14 张卡在 143–150 行"的**正确**读数当成错的改掉（差点把对的改错，比两个数字不一致更贵）。
根因：core.autocrlf=true 下工作区与仓库行尾不同；计数口径不一——**唯一有效口径 = `[IO.File]::ReadAllLines($p,[Text.Encoding]::UTF8).Count`（含空行）；禁 Get-Content（GBK 少算可达 56 行）、禁 Measure-Object -Line、禁字节 0x0A 计数**。
修法（实测）：数字带四元组（值+口径+时点+域），声明贴命令原文；字节对拍必须先行尾归一；判提交树门禁用 `git -c core.autocrlf=false archive 起点锚点提交`；autocrlf=true 的仓库禁 `git stash`；新项目沿用模板根的 `.gitattributes`（`* text=auto eol=lf`）。
下次定位：对拍失败；两处数字对不上；"行数/条数"类声明。
证据：外部台账 `batch02-bundle.md:344` · `batch06-motion.md:1014`（B-79）· `batch01-deletions.md:79` · `batch02-bundle.md:68`（原项目分册，未随模板分发，仅作溯源）
来源：Entropydecrease 台账（14/14 全批皆然，第一大系统性弱点）· 事故 2026-09-11，2026-09-13 并入模板
**最小复现（2026-10-07 实测，39 字节）**：三行中文文件（UTF-8 无 BOM，行尾 LF ×3）——`(Get-Content $f).Count` = **2**、`Get-Content -Encoding UTF8` = **3**、`ReadAllLines(UTF8)` = **3**。**机制也已实测**（不再只是"疑似"）：同一份字节按系统码页（936/GBK）解码后 **LF 由 3 个变 2 个**（0x0A 被当成前一个双字节字的低位字节吃掉）⇒ 按码页读的行数**必然**少算，与行尾、与文件大小都无关，只与"内容里有中文 + 读法没写 `-Encoding`"有关。
最近确认：2026-10-07（检测器误报批：卡面行数读数复现 + 机制实测 + 最小复现 39 字节）
