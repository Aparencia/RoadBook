# 编辑工具改写 .ps1 会静默丢 BOM → PS 5.1 ParserError
复发次数: 2
作用域: 全局（所有 .ps1 入口：check / doctor / gate / orphans / security / _qc）
最近复发: 2026-10-07
现象：`check.ps1` 先被判「禁止运行脚本」，加 `-ExecutionPolicy Bypass` 后又炸 ParserError，中文判词显示成 `鏈壒 0 鎻愪氦`（UTF-8 被按 GBK 读）；同一批 doctor / orphans / gate / security 四个脚本中文**全部正常**——差别只有一个：出问题那个文件本轮被编辑工具改写。**2026-10-07 复发且换了皮肤**：用 `edit` 改 `_qc/check.ps1` 的断言后前三字节变成 `23 20 5F`，报错却落在**第 90 行**（我改的是第 640 行）——症状离改动点 550 行，极易误判成"别处坏了"。
根因：脚手架写入的 .ps1 带 UTF-8 BOM；通用编辑/写入工具按「UTF-8 无 BOM」落盘，BOM 被**静默**丢弃。PS 5.1 对无 BOM 的 .ps1 一律按系统码页（中文机 = GBK）解码。
修法（实测）：改完任何 .ps1 立刻验前三字节必须是 `EF BB BF`；丢了就重建：`[IO.File]::WriteAllText($p,[IO.File]::ReadAllText($p,[Text.Encoding]::UTF8),(New-Object Text.UTF8Encoding($true)))`。**判定口径：`edit` 工具改过的 .ps1 一律按"已丢 BOM"处理，改完必须重写一次。**
下次定位：.ps1 报 ParserError / 中文乱码 / 禁止运行脚本，且**只有"被编辑过的那一个"**出问题 → 先看前三字节，别去改脚本逻辑；**报错行号与本次改动位置对不上时尤其要先怀疑它**。
证据：实测 `check.ps1` 前三字节 = `23 20 63`（`# c`），其余六个 .ps1 入口 = `EF BB BF`；同一命令重建 BOM 后 ParserError 消失，门禁只剩「工作树不干净」一项。2026-10-07 复现：`_qc/check.ps1` = `23 20 5F` → 重建后 `通过 360 项；失败 0 项`、退出码 0。
