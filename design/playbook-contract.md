# Playbook 写作契约（建卡者必读）

> 本契约是 40 张卡（0-1 驱动卡 + 39 张动作卡）统一的质量标准：中文版 `playbook/` 与英文版 `playbook_EN/` **同受约束**。任何一份不符合本契约 = 不合格，必须返工。
> 设计依据见 `v6-design.md`（§1 公理、§4 卡集、§4.1 中英文件名对照、§8 写作规范）；翻译口径见 `glossary-en.md`。

---

## 1. 卡的文件规范

- 中文卡位置：`playbook/` 目录下，文件名 = `<卡号>-<卡名>.md`（如 `playbook/2-2-需求范围.md`）。卡号 = 阶段号-行为序号（阶段 0 驱动层 / 1 立项期 / 2 需求期 / 3 设计期 / 4 实现期 / 5 交付期 / 6 运行与治理期 / 7 特殊变更期）
- 英文卡位置：`playbook_EN/` 目录下，文件名 = `<卡号>-<英文名>.md`（如 `playbook_EN/2-2-scope-definition.md`）。文件名逐字取自 `v6-design.md` §4.1 对照表，**少一张或名字不一致 = 校验器判红**
- 两份**逐张对应**：同卡号、同段数、同段序、同判据（数字/阈值/命令/路径/卡号/清单条目数量逐字对应）
- 头部元信息 **≤3 行**，格式固定：

```markdown
# 卡 2-2 · 需求范围（功能档必走；S 档简版）
> 触发：功能调研通过后 ｜ 产物：docs/specs/<日期>_<slug>/SCOPE.md ｜ 下一张：4-1 分批编码
```

英文版头部逐字对应（映射表见 `glossary-en.md` §3）：

```markdown
# Card 2-2 · Scope definition
> Trigger: after feature research passes | Output: docs/specs/<date>_<slug>/SCOPE.md | Next: 4-1 Batch coding
```

不写"来源/定位/生成日期/维护者"等长前缀——打开即见正文。

- 正文结构 = **四段**，用 `---` 分隔，段标题固定：

| 中文 | 英文 |
| :--- | :--- |
| `## ① 开工确认` | `## ① Start confirmation` |
| `## ② 执行` | `## ② Execution` |
| `## ③ 证据回执` | `## ③ Evidence receipt` |
| `## ④ 状态回写` | `## ④ State write-back` |

- 全文 **≤150 行**（含头部与空行）。超了就砍背景解释，砍不掉就说明该卡职责过多，报回设计者。**2026-10-03 起本轮降级为观测项**（用户裁决"取消行限制、卡片量限制，先完整后续再进行精简"）：`_qc/check.ps1` 照常测量并列出超限卡，但不拦红；下一轮精简时恢复为硬断言。**不许用"超限"当删判据腾地方的理由**——超限的合法处置只有"砍背景解释"或"拆卡"
- 每张卡末尾必须有**固定收尾语**（两份各一份，见 §2 ④）

## 2. 四段结构的内容要求

### ① 开工确认
- 要求 agent 先复述本次任务（用人话）、列出假设清单
- 提 **≤5 个澄清问题**（能删则删；能自己从项目文件查到答案的不许问人）
- **每个问题自带推荐答案**（2026-10-04 补）：先给出你推荐的答案与理由，用户回一个词即可；**事实由你查**（文件、命令、git），**决定由用户拍**（取舍、优先级、验收标准）。禁止问没有推荐答案的空问题（"你想怎么做？"）
- **逐字引用本卡的检查清单原文**（从 §② 里挑最关键的 3~5 条）——这是防绕过机制：引不出原文 = 输出作废
- 声明本卡产物落点与下一张卡
- **这条不是形式**：Violating the letter of the rules is violating the spirit of the rules. / 违反规则的字面就是违反规则的精神。（2026-10-03 补，源自 superpowers `writing-skills` 内化）

### ② 执行
- **只写动作，不写要求**。每条是"做 X"，不是"应该注意 X"
- 每个判断给 **❌反例 / ✅正例** 对照（模拟实测：反例比定义有效十倍）
- **合理化红旗表**：本卡已知会被绕过的判断，必须在 ② 段开头给一张两列表 `| 你会想 | 事实 |`（英文 `| You may think | Reality |`），**≥3 行**。表里写**真实出现过的原话**（实战记录或模拟实验里的说法，逐字照抄），不是编造的反例——编的反例拦不住任何人。存量 39 张动作卡**不追溯**：哪张卡出现第二次同类绕过，就在哪张卡补表（判定节奏同 6-6 卡"信号 ≥2 次复现才改规则"）
- **判据分界**：能用正则或脚本判的一律下沉为断言（零 token、不会忘、不会假绿）；卡里的散文只留给需要判断力的事。机器能判却只写在卡里 = 等于没判
- 每个人要做的判断给**照着念的清单**（用户可以逐条念给 agent 听）
- 每个命令给**可直接复制的一行**（Windows 优先 PowerShell；必须 bash 时附一行 Git Bash 跑法）。命令**一律用正斜杠路径**（`powershell -NoProfile -File _qc/check.ps1`），且**禁止出现 `<占位符>`**——`<` 在 Windows PowerShell 是保留运算符，直接粘贴会 `ParserError`；要给变量就写成"先赋值再调用"（如 `$anchor = git rev-parse HEAD` 再 `-Anchor $anchor`）
- 分批与停下点显式写明（如编码卡 ≤300 行/批）
- 禁令用"禁止"列表单独列，违反 = 输出作废
- 判据**内联**：本文需要的一切阈值、清单、格式都在本卡内写全。**禁止**引用 playbook/ 内其他卡、design/、_archive/（对项目文件的引用可以且应该写具体路径）。此禁令**两份卡都适用**：英文版同样不许写"see card 4-2"

**形态选择（先判失败类型，再选写法；2026-10-03 补，源自 superpowers `writing-skills` 内化）**：同一个判断用错形态，写多少遍都不管用。按"这张卡要防的失败长什么样"选形态，四类失败对四种形态：

| 失败长什么样 | 形态 |
| :-- | :-- |
| 知道却违反 | 禁令 + 合理化红旗表 |
| 输出形状不对 | 正向配方（照抄一遍这个输出长什么样） |
| 漏必需元素 | 结构槽位（REQUIRED 字段，缺了脚本报错） |
| 依赖条件的规则 | 写成可观测谓词的条件句 |

**硬禁令**：禁写"除非确实需要""一般情况"这类细微差别条款——例外的唯一写法是可观测谓词（"当 X 字段为空时……"），不许写"视情况而定"。

**写作教义（2026-10-04 补，源自 mattpocock/skills `writing-for-agents` 内化）**：

- **正说优先**：先写"做什么"（正面配方），再考虑禁令。**否定式本身是失败模式**——禁令会把被禁行为拉进上下文；只有无法正说的硬护栏才写禁令，并同时给正面目标。
- **no-op 测试**：写完一句问自己"删掉它，agent 的行为会变吗？"不变 = 删掉，或改写成可执行判据。"读起来有道理"不算数。
- **信息阶梯**：能写进步骤的不另开一节；要引用就先给步骤再给引用；同一事实只写一处——**文档是 cache，命令与文件是事实源**。
- **触发词唯一**：一个分支只留一个触发词；同义改写 = 同一个分支写两遍，会互相打架。
- **leading words**：用模型已经认识的词收束一串形容词（把"快、确定、开销低"收成"紧"），不造新词。

### ③ 证据回执
- 规定本卡收尾必须粘贴的证据：命令真实输出 / 文件路径 / 提交哈希
- "完成"的声明必须逐条对应证据；没有证据 = 未完成
- 需要跑 guardrail 的卡，写明命令：`powershell -NoProfile -File check.ps1`（退出码必须 0）
- **阶段顺序**：状态回写（STATE.md / 账本 / registry / 计数）必须发生在**提交之前**；末段固定"回写状态 → 提交 → 复跑 check.ps1 取 0"。提交后才回写状态 = 收工必脏树，属违规

### ④ 状态回写
- 要求 agent 更新 `STATE.md` 的哪些字段（具体到字段名）
- 指明**下一张卡**（卡号+名称），以及"S 档可跳到哪、L 档加走哪"的分支说明
- 固定收尾语，逐字使用：
  - 中文：`等待你裁决。回复"继续"执行下一张卡，或说新指令。`
  - 英文：`Awaiting your verdict. Reply "continue" to run the next card, or give a new instruction.`

**渐进披露三级（2026-10-04 补，源自 anthropics/skills `skill-creator` 内化）**：卡的体积不是审美问题，是装载问题——入口越厚，被截断、被跳读的概率越高。三级各司其职：

| 层 | 装什么 | 上限 | 什么时候载入 |
| :-- | :-- | :-- | :-- |
| metadata | `SKILL.md` frontmatter 的 `name` + `description`（宿主只注入这两项） | description ≤500 字符、约 100 词；只回答"什么时候用 / 什么时候不用" | 常驻 |
| 正文 | `SKILL.md`、0-1 驱动卡、被路由到的卡 | 单卡 ≤150 行；正文文件 <500 行 | 触发时 |
| 资源 | 脚本、样例、参考资料 | 不设总量上限；单个参考文件 >300 行时开头给目录 | 按需读取 |

超限的**唯一**合法处置是加一层并给明确指针（"想看 X 去 Y"），**不许删判据腾地方**；指针指向的文件必须真实存在（幽灵指针 = 路由在骗人，`_qc/check.ps1` 判红）。

## 3. 双语同步义务

- **读取顺序**：agent 执行任何卡时，先读 `playbook_EN/` 下同卡号的英文执行版；中文版 `playbook/` 是权威源与人类阅读版
- **冲突裁决**：两者冲突——**判据以中文版为准**；**措辞歧义以英文版为准**
- **同批修改**：改判据必须两份同批改。只改一份 = `_qc/check.ps1` 判红，等于没改
- **英文版不许增删**：数字、阈值、命令、路径、卡号、清单条目数量**逐字对应**。英文版只允许把中文的含糊表述**显式化**（消歧），并在该行末尾标 `[disambiguated]`；不许增删规则、放宽或收紧判据
- **新术语先入表**：新术语先写进 `glossary-en.md` 的术语表（唯一写法），再翻卡。术语表没有的，保留中文原词并加括号注释（`（<中文原词>）`），**不许自造近义词**
- **结构逐段对应**：段号、段序、段标题一一对应（映射表见 `glossary-en.md` §3）；`❌` / `✅` 原样保留，`【…】` 段标记写成 `[ … ]`
- **反向义务**：中文版被英文版消歧后修正，两份**同一批提交**
- **验收**：两份改完后跑 `powershell -NoProfile -File _qc/check.ps1`——43 张逐张对齐，缺一张或结构不一致 = 判红；母版改动 = 退出码 0 + 一次提交 + `git push`

## 4. 语言与受众

- 中文正文，技术名词保留英文；英文版按 `glossary-en.md` 术语表逐词对应，不做意译
- 受众：会用 agent 但没系统学过软件开发的人。默认读者**不懂**：分支策略、环境变量、迁移、容器、覆盖率
- 涉及这些概念时：一句人话解释 + 可复制命令，不展开教程
- 语气：直接、具体、零客套。不写"建议""可以考虑"，写"做 X"

## 5. 与机制文档的对应（卡内怎么提项目文件）

| 卡里的事 | 指向的项目文件 |
| :--- | :--- |
| 查/回写组件 | `docs/registry/COMPONENTS.md` |
| 查/回写表结构 | `docs/registry/DATA_DICT.md` |
| 查/回写接口与错误码 | `docs/registry/APIS.md` |
| 查架构约束/新代码落点 | `docs/ARCHITECTURE.md` |
| 部署/回滚/备份 | `docs/RUNBOOK.md` |
| 想法登记 | `docs/pool/IDEAS.md` |
| 决策记录 | `docs/decisions/<类型>_<日期>_<主题>.md` |
| 任务工作区 | `docs/specs/<日期>_<slug>/` |
| 债务登记 | `docs/TECH_DEBT.md` |
| 教训沉淀 | `docs/lessons/<日期>_<主题>.md` |
| 版本详情 | `docs/versions/vX.Y.Z.md`；索引=根 `CHANGELOG.md` |
| 归档 | `docs/archive/<日期>_<slug>/`，用 `git mv`，原子提交，**禁止 `git add -A` / `git add .`** |
| 状态仪表盘 | `STATE.md`（项目根） |
| 环境自检 / 收工仪式 | `powershell -NoProfile -File doctor.ps1` / `powershell -NoProfile -File check.ps1` |

## 6. 常见错误（建卡者自查）

- ❌ 在 ① 里复述一遍设计原理（原理属于 design/，卡里只留一句"为什么"）
- ❌ 检查清单写抽象要求（"注意性能"）——必须写可执行动作（"跑 X 命令，看 Y 指标"）
- ❌ 引用其他卡的内容而不内联（"按 4-2 卡的七维度执行"）——把七维度抄进本卡；英文版同样判红
- ❌ 门禁让 agent 自己宣布通过——永远只给"建议色 + 依据"，裁决是人
- ❌ 产物路径含糊（"放到 docs 下"）——写到具体文件名模式
- ❌ 超行数后偷偷压缩四段结构——四段是骨架，宁可靠拢行数也不许砍段
- ❌ 只改一份语言（改了中文卡不翻英文版，或反之）——两份同批改，只改一份 = 判红
- ❌ 英文版另起编号、另造卡名或另命名文件——文件名与卡号逐字取自 `v6-design.md` §4.1
- ❌ 英文版自行增删清单条目、数字、阈值或命令，或把含糊表述"翻译"成新规则——只允许显式化并标 `[disambiguated]`
- ❌ 自造术语近义词而不入 `glossary-en.md` 术语表——先入表再翻卡
- ❌ 合理化红旗表写成假想反例（"agent 可能偷懒"）——必须逐字写真出现过的说法，编的拦不住人
- ❌ 机器能判的判据只写成散文（能写成断言却不下沉脚本）——零 token 的检查下沉到母版 `_qc/check.ps1` 或项目 `check.ps1` / `gate.ps1`
- ❌ 用否定式堆砌规则（"不要 X""别 Y""避免 Z"）——禁令会把被禁行为拉进上下文；能正说就正说，硬护栏才写禁令并配正面目标
- ❌ 写 no-op 句子（删掉后 agent 行为不变）——删掉，或改写成可执行判据
- ❌ 同一分支写多个同义触发词——一个分支一个触发词，同义改写 = 同一分支写两遍
