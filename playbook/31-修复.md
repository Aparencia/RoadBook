## ① 开工确认

收到开工指令后，先回执：

1. **根因复述**：一句话（从 RCA.md 引用）。
2. **修复方案**：改哪些文件/怎么改，以及"为什么这是最小改动"。
3. **起点锚点声明**：执行 `git rev-parse HEAD` 并回显（写进 STATE.md）。
4. **引用检查清单原文**（逐字粘贴本卡 §② 的"修复范围双维锁"阈值表）。

---

## ② 执行

**第 0 步：记录起点锚点**（同 23 卡，禁止跳过）。

**动作 1：最小改动修复**
- 只修根因指向的问题，不做任何"顺手"的事。
- **修复范围双维锁**：

| 信号 | 判定 | 处置 |
| :-- | :-- | :-- |
| ≤3 文件 且 ≤100 行 | ✅ 正常 | 继续修 |
| >3 文件 或 >100 行 | ⚠️ 黄牌 | 停下，向用户解释为什么最小修复需要这么大，获批再继续 |
| >600 行 或 要动表结构 | 🔴 红牌 | 拆成独立任务，回用户重新规划 |

- 修复方案有多个时，先列候选（A/B + 取舍）再推荐，由人挑。

**动作 2：顺手问题登记制**
修 A 时发现 B 有问题 → 登记 `docs/TECH_DEBT.md`（TD-序号 + 来源=BUG-xxx 修复过程），**不许顺手修**。
❌ 反例："反正路过这个文件了，把那个过时写法也改了"
✅ 正例："TD-012 已登记：同文件存在过时写法，建议另行清偿"

**动作 3：提交**

```powershell
git add <精确文件列表>
git commit -m "31 fix(<bug名>): <修了什么> (BUG-xxx)"
```

**禁令：**
- 禁止 `git add -A` / `git add .`
- 禁止顺手重构/顺手升级依赖/改无关文件
- 禁止跳过"黄牌确认"直接大改
