## ② 执行

**先给每一项标 Merge Danger（发布前逐项标在下面两栏里，然后才走发布七查）：**

| 项 | 判什么 | 怎么判 |
| :-- | :-- | :-- |
| **单向门 / 双向门** | 出错后能不能原样退回来 | **单向门** = 出错后无法原样回退：删数据、改表结构、对外承诺（已告知用户的时间/价格/功能）、改接口契约；**双向门** = 撤销即回到原状（改文案、加开关、加日志） |
| **爆炸半径** | 出事时影响几个用户 / 几个模块 | 写具体数字或范围（"0 个真实用户""全部 3 个模块"）；写不出就按大半径处理 |

**判据：单向门 + 大半径 = 必须有人在场裁决（红线）；且回滚预案必须先演练过——演练未做 = 不许发**（演练记录附在回执里）。双向门 + 小半径可自行发布。

**发布七查：**

**① 部署路线（按项目实况选，写进 RUNBOOK）**

| 路线 | 适用 | 要点 |
| :-- | :-- | :-- |
| 本地演示 | 只有自己用 | doctor + check 通过即算发布 |
| 静态托管 | 纯前端 | Vercel/Netlify 连仓库自动部署；配好环境变量 |
| 托管平台 | 带后端 | Railway/Render/Fly.io；数据库用平台托管实例；秘钥进平台后台不进代码 |
| 云服务器 | 自管 | 域名+HTTPS 必配；服务器加固另立任务 |

**② 前置全绿**：`check.ps1` 退出码 0 + 行为验收清单（最近任务的）过一遍。

**③ 数据与迁移**：本次含表结构变更？迁移由**人执行**（不可委托）；执行前先跑 RUNBOOK §5 备份。

**④ 回滚预案（先写预案再发布）**：写清"发布坏了怎么退"——上一版本重部署命令 / 数据回滚路径，存入版本详情。
❌ 反例："回滚：git revert（到时候再说）"（没有具体命令与数据处置，出事时只能临场发挥）
✅ 正例："回滚：`git checkout v0.2.0` 重部署；数据无破坏性迁移（L1 追加），无需回滚数据；确认点：打开 /health 返回 200"

**⑤ 版本三对齐**：
- 根 `CHANGELOG.md`：把"未发布"节整理成正式版本节（新增/变更/废弃/修复）
- 版本号：0.x 阶段随意；1.x 起破坏性变更升 MAJOR 并写"升级注意"
- `docs/versions/vX.Y.Z.md` 详情：做了什么/为什么/已知问题/部署动作/回滚点
- 三处版本号一致（CHANGELOG = 详情文件名 = tag）

**⑥ 打 tag（agent 执行；提交跑绿 + 三对齐核对通过之后）**：
```powershell
$ver = 'v0.3.0'                          # 本次版本号，三处必须一致
git tag -a $ver -m "release $ver"        # 注解式 tag；禁止轻量 tag、禁止 git tag -f
git push origin $ver                     # 有远端时
```
Expected：`git tag -a` 成功**没有任何回显**（本机沙箱实测 stdout 0 行、退出码 0）⇒ 空输出 ≠ 没打上：用 `git tag -l $ver` 复核（打 `v0.3.0`），或 `git for-each-ref --format='%(refname:short) %(objecttype)' refs/tags` 看类型 —— 注解式打 `v0.3.0 tag`、轻量 tag 打 `light commit`（这条把"禁止轻量 tag"变成可判的读数）。`git push origin $ver` 首次打 `To <远端>` + ` * [new tag]         v0.3.0 -> v0.3.0`、退出码 0；**没动过的 tag 重复推**打 `Everything up-to-date`、退出码 0；**移动过的 tag 再推**打 ` ! [rejected]        v0.3.0 -> v0.3.0 (already exists)` + `error: failed to push some refs to '…'` + `hint: Updates were rejected because the tag already exists in the remote.`、**退出码 1** —— 这就是"已发布的 tag 不许移动"的机械证据；而 `git tag -a -f` 会打 `Updated tag 'v0.3.0' (was <旧短哈希>)`，看到这行就说明动了不该动的 tag。
❌ 反例：CHANGELOG 写 v0.3.0、详情文件叫 v0.3.1.md、tag 打 v0.30（三处对不上，回滚时找不到对应版本）
❌ 反例：发现打错位置就 `git tag -f` 覆盖（**已发布的 tag 不许移动或删除**——它是别人核对版本时唯一的锚点）
✅ 正例：三处都是 v0.3.0 —— CHANGELOG 节标题 / `docs/versions/v0.3.0.md` / `git tag v0.3.0`

**⑦ 收尾同步**：docs/RUNBOOK.md §1 部署节更新；条件文档触发检查——有真实用户→建 USER_GUIDE；收集 PII 且公开→PRIVACY；开源→LICENSE。

**禁令：**
- 禁止 agent 执行部署（不可委托，人执行）
- 禁止移动或删除已发布的 tag（`git tag -f` / `git push --force` 覆盖 tag 一律违规）
- 禁止跳过回滚预案直接发（"应该没问题"不是预案）
- 禁止版本三处对不上就发布
