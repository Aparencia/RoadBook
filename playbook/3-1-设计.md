## ② 执行

**动作 1：数据设计 → DESIGN.md"数据字典 diff"节（逐行）**
格式：`表 | 字段 | 类型 | 校验 | 敏感度`。敏感度按下表标，错标会漏加密与脱敏：

| 级 | 定义 | 例 |
| :-- | :-- | :-- |
| D1 | 公开数据，泄露无实害 | 产品名、公开设置 |
| D2 | 内部数据，泄露不适但不伤人 | 笔记内容、使用记录 |
| D3 | 个人信息，能定位到人 | 姓名、邮箱、手机号 |
| D4 | 高敏，泄露即事故 | 密码、token、支付、证件号 |

❌ 反例：user 表 email 标 D1（错——是 D3，日志与导出必须脱敏）
✅ 正例：`user | email | varchar(255) | 格式校验 | D3`

**动作 2：接口设计 → DESIGN.md"接口契约"节（逐行）**
格式：`路径 | 方法 | 用途 | 错误码 | 鉴权`，每行附一对最小 JSON 请求/响应示例（≤4 行）。新错误码在行内声明；本期不实现但契约先行的占位接口，响应写 503 + **9xxx = 未实现占位**，行内必须标 `planned` 并登记 `docs/registry/APIS.md` 错误码列（未登记 = 设计未通过）。

**动作 3：组件影响 → DESIGN.md"组件影响"节**
逐行：`页面 | 界面元素 | 人话标识 | 文件 | 影响面`。用 docs/registry/COMPONENTS.md 的人话标识列定位；查不到的元素标"待建行"。新页面写明路由落点。

**动作 4：迁移三件套（涉及表结构时）**
落点 `migrations/<YYYYMMDD>_<slug>_up.sql / _down.sql / _seed.sql`（框架型项目用对应迁移文件，命名同规则）。
- **up**：正向建表/改字段。
- **down**：手写精确反向回滚（框架 autogenerate 的 downgrade 不可靠），必须能恢复到 up 之前。
  ❌ 反例：down 只写 `DROP TABLE users;`（把表里原有数据一起毁掉）
  ✅ 正例：改列的 down 先备份旧列数据再恢复；删对象的 down 只删 up 建的对象
- **seed**：开发用假数据（`张三 test@example.com` 这类），必须幂等（重复执行不报错）；禁止真实个人信息。

**down 必须人本地空跑验证（涉及表结构时；无表结构 → ④ 写 N/A + STATE.md 裁剪记录依据。agent 只给三条精确命令）：**
```powershell
# 人依次执行，agent 按实际栈把 $up/$down 换成真实命令后交付：
# 1) powershell -NoProfile -File check.ps1
# 2) $up   = 'psql -d app -f migrations/20260912_bills_up.sql'
# 3) $down = 'psql -d app -f migrations/20260912_bills_down.sql'
```
down 跑完用一条查表命令（agent 给出）贴回输出，与迁移前一致 = 第 ④ 证成立。

**动作 5：破坏性分级（先判再动，🔴 即红牌）**
🟢 L1 纯追加（新表/可空列/新索引）→ 直接做。
🟡 L2 改类型/加 NOT NULL/重命名/回填 → 必须有备份方案 + down 可回滚。
🔴 L3 删表删列/拆并表/改主外键语义 → **红牌拆任务**：本任务只做加新与双写，破坏步骤另立任务单独批。
❌ 反例：一个迁移同时"加 status 列 + 删旧 state 列"
✅ 正例：任务 A 加 status 列并双写；任务 B（另批）确认切换后删 state 列

**动作 6：改造 vs 重写（先算改动面，再动手）**
改动面 = 本任务需改动的行数 ÷ 目标文件现有行数。判据（内联，不许临场放宽）：
- < 40% → **就地改**（默认路径，不需要额外理由）。
- **≥ 40% → 一律需写明理由并获用户确认**（就地改与重写都要写；回执缺理由或缺确认 = 设计未通过）。
- \> 60% 且旧逻辑无复用价值 → 才允许重写，两条同时成立才行。

选"重写"时，设计段必须交付两样（缺一 = 设计未通过）：
1. **等价性证据计划**：三选一并写明具体命令——①旧测试全绿（贴测试命令）②快照对比（贴生成 + 比对命令）③关键路径手测清单（逐条写操作与预期结果）。
2. **旧实现退役计划**：写明旧实现在哪个批次删、删除条件（可判定）、是否需要并行态登记——合法保留理由只有三种：灰度/回滚带期限、对外兼容契约带弃用期、证据留存（证据留存的答案是 git 历史，工作树不许留第二份）。

❌ 反例：直接新建 `xxx_v2.ts` 实现一遍，旧文件留着"以后再说"
✅ 正例：就地改造 + 同批删除旧实现 + 回执贴删除证据（`git diff --stat` 里的删除行）

**设计通过四证（缺一 = 设计未通过）：**

```text
① DATA_DICT diff 每行都标了敏感度 D1~D4
② APIS 每行都含错误码与鉴权列
③ 组件影响清单已列出（含"待建行"标注）
④ down 由人本地空跑通过，输出已贴回（无表结构 → ④ 写 N/A + 裁剪记录依据）
```

**禁令：**
- 禁止只写 up 不写 down
- 禁止 agent 执行 SQL / 迁移（不可委托清单项）
- 禁止 seed 用真实个人信息
- 禁止把 L3 破坏性变更藏进普通迁移
- 禁止设计未获人批准就进 4-1
