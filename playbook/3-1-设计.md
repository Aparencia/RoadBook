## ② 执行

**合理化红旗表（开工时逐条念；出现任一条 = 停下按本卡补做）**

| 你会想 | 事实 |
| :-- | :-- |
| 先把表结构写完，接口和组件以后再补 | 设计通过四证缺一即未通过；三张 diff 必须同批齐全 |
| down 让框架 autogenerate 就行 | 框架生成的 downgrade 不可靠；down 必须手写，且能恢复到 up 之前 |
| 这些是"业界最佳实践"，不用写出处 | 无出处的量化与"最佳实践"是 AI 味签名；判据必须落到本项目的表 / 字段 / 路径 / 命令 |

**动作 0：设计计划前置（动手前先写，≤10 行；不写就打开 DESIGN.md = 本卡未开工）**
① 一句话目标 ② 本次要钉死的对象（表 / 接口 / 组件各一行，指回 SCOPE 条目）③ 取舍与判据（每条写"选 A 不选 B，因为 …"，判据可测）④ 明确不做（Won't Have 原文）⑤ 预发六轴自评要跑（见动作 9）
❌ 反例：直接打开 DESIGN.md 从第一张表写起 ｜ ✅ 正例：先贴 10 行计划，再逐节填

**DESIGN.md 九节骨架（按此排序填写；缺任意一节 = 设计未通过）**
1 目标与非目标（含 Won't Have 原文）｜2 数据字典 diff（表 | 字段 | 类型 | 校验 | 敏感度）｜3 接口契约（路径 | 方法 | 用途 | 错误码 | 鉴权 + 最小 JSON）｜4 组件影响（页面 | 界面元素 | 人话标识 | 文件 | 影响面）｜5 迁移三件套（up / down / seed 的路径）｜6 破坏性分级（L1 / L2 / L3 + 依据）｜7 改造 vs 重写（改动面 % + 理由）｜8 决策记录（三要件同时成立才写）｜9 被否方案（每条一行否决理由）

**动作 1：数据设计 → DESIGN.md"数据字典 diff"节（逐行）**
格式：`表 | 字段 | 类型 | 校验 | 敏感度`；敏感度按下表标（级 | 定义 | 例），错标会漏加密与脱敏——D1 公开数据，泄露无实害（产品名、公开设置）｜D2 内部数据，泄露不适但不伤人（笔记内容、使用记录）｜D3 个人信息，能定位到人（姓名、邮箱、手机号）｜D4 机密，泄露造成重大损害（密码、token、支付、证件号）。
❌ 反例：user 表 email 标 D1（错——是 D3，日志与导出必须脱敏）｜✅ 正例：`user | email | varchar(255) | 格式校验 | D3`

**动作 2：接口设计 → DESIGN.md"接口契约"节（逐行）**
格式：`路径 | 方法 | 用途 | 错误码 | 鉴权`，每行附一对最小 JSON 请求/响应示例（≤4 行）。新错误码在行内声明；本期不实现但契约先行的占位接口，响应写 503 + **9xxx = 未实现占位**，行内必须标 `planned` 并登记 `docs/registry/APIS.md` 错误码列（未登记 = 设计未通过）。

**动作 3：组件影响 → DESIGN.md"组件影响"节**
逐行：`页面 | 界面元素 | 人话标识 | 文件 | 影响面`。用 docs/registry/COMPONENTS.md 的人话标识列定位；查不到的元素标"待建行"。新页面写明路由落点。

**动作 4：迁移三件套（涉及表结构时）**
落点 `migrations/<YYYYMMDD>_<slug>_up.sql / _down.sql / _seed.sql`（框架型项目用对应迁移文件，命名同规则）。**up** 正向建表/改字段｜**down** 手写精确反向回滚（框架 autogenerate 的 downgrade 不可靠），必须能恢复到 up 之前——❌ 反例：down 只写 `DROP TABLE users;`（把表里原有数据一起毁掉）｜✅ 正例：改列的 down 先备份旧列数据再恢复；删对象的 down 只删 up 建的对象｜**seed** 开发用假数据（`张三 test@example.com` 这类），必须幂等（重复执行不报错）；禁止真实个人信息。

**down 必须人本地空跑验证（涉及表结构时；无表结构 → ③ 证据回执第 4 项写 N/A，并在 `## ④ 状态回写` 的 `裁剪记录` 写依据。agent 只给三条精确命令）：**
人依次执行，agent 按实际栈把 `$up`/`$down` 换成真实命令后交付：① `powershell -NoProfile -File check.ps1` ② `$up = 'psql -d app -f migrations/20260912_bills_up.sql'` ③ `$down = 'psql -d app -f migrations/20260912_bills_down.sql'`。down 跑完用一条查表命令（agent 给出）贴回输出，与迁移前一致 = 第 ④ 证成立。

**动作 5：破坏性分级（先判再动，🔴 即红牌）**
🟢 L1 纯追加（新表/可空列/新索引）→ 直接做｜🟡 L2 改类型/加 NOT NULL/重命名/回填 → 必须有备份方案 + down 可回滚｜🔴 L3 删表删列/拆并表/改主外键语义 → **红牌拆任务**：本任务只做加新与双写，破坏步骤另立任务单独批。
❌ 反例：一个迁移同时"加 status 列 + 删旧 state 列"｜✅ 正例：任务 A 加 status 列并双写；任务 B（另批）确认切换后删 state 列

**动作 6：改造 vs 重写（先算改动面，再动手）**
改动面 = 本任务需改动的行数 ÷ 目标文件现有行数。判据（内联，不许临场放宽）：< 40% → **就地改**（默认路径，不需要额外理由）｜**≥ 40% → 一律需写明理由并获用户确认**（就地改与重写都要写；回执缺理由或缺确认 = 设计未通过）｜\> 60% 且旧逻辑无复用价值 → 才允许重写，两条同时成立才行。
选"重写"时，设计段必须交付两样（缺一 = 设计未通过）：1. **等价性证据计划**：三选一并写明具体命令——①旧测试全绿（贴测试命令）②快照对比（贴生成 + 比对命令）③关键路径手测清单（逐条写操作与预期结果）。2. **旧实现退役计划**：写明旧实现在哪个批次删、删除条件（可判定）、是否需要并行态登记——合法保留理由只有三种：灰度/回滚带期限、对外兼容契约带弃用期、证据留存（证据留存的答案是 git 历史，工作树不许留第二份）。
❌ 反例：直接新建 `xxx_v2.ts` 实现一遍，旧文件留着"以后再说"｜✅ 正例：就地改造 + 同批删除旧实现 + 回执贴删除证据（`git diff --stat` 里的删除行）

**动作 7：决策记录三要件（三条同时成立才写进 `docs/decisions/`）**
一条记录只有在**难以回退** 且 **出人意料** 且 **真有权衡**三条**同时**成立时才写；缺任意一条就不写——写了只是噪音，会把真正需要复读的记录淹掉。
❌ 反例："日志级别从 info 调到 debug"（随时可回退、结果不出人意料、没有取舍 → 不写）｜✅ 正例："订单金额改存整数分"（改回去要动迁移与历史数据 = 难以回退；团队原以为用两位小数 = 出人意料；有精度与兼容取舍 = 真有权衡 → 写一条）

**动作 8：被否方案（DESIGN.md 必须有「被否方案」段）**
每个被否的方案写一行"它为什么不选"，供以后重审时先读；重审同一方案时，先把这一行原文贴出来再讨论——不贴 = 从零重议，上次的判断白做。
❌ 反例：否掉"加消息队列"后一字不写 → 下次有人再提，又从头讨论一遍｜✅ 正例：`被否方案：消息队列 —— 否决理由：本期单机部署，运维成本 > 收益（2026-09-12）`

**动作 9：预发六轴自评（每条 1~5 分；任一 <3 触发修订轮。最多 3 轮，第 3 轮仍 <3 = 计划本身错了，回去问用户）**
（轴 | 问自己 | 5 分长什么样）依据性：每条判据能不能指到具体表 / 字段 / 路径 / 命令？→ 判据全部落在本项目对象上，没有"最佳实践"｜可逆性：出错能不能回退？→ 每个破坏性动作都有 down 或双写方案｜最小面：有没有能不改的东西被改了？→ 改动面 < 40%，并列了"故意没碰"的清单｜可测性：判据能不能被判红？→ 每条判据配一条可跑命令或可观察现象｜一致性：与 registry / ARCHITECTURE 是否一致？→ 三张 diff 与 registry 三件套逐条对得上｜演进空间：4-1 能不能只照本设计做，不再做设计决策？→ 4-1 不需要回头改设计。
自评分与修订轮次原文写进 ③ 回执第 9 项。

**动作 10：设计文档自查（在项目根跑；exit 1 = 本卡未完成）**
变量名一律 ASCII：Windows PowerShell 5.1 读无 BOM 的 .ps1 时中文变量名会报『字符串缺少终止符』。把 `$d` 换成真实 DESIGN.md 路径后跑：
```powershell
$d = 'docs/specs/20260912_export/DESIGN.md'; $l = @(Get-Content $d -Encoding UTF8); $sec = @('目标与非目标','数据字典','接口契约','组件影响','迁移三件套','破坏性分级','改造 vs 重写','决策记录','被否方案'); $miss = @($sec | Where-Object { -not ($l -match [regex]::Escape($_)) }); $bad = @($l | Where-Object { $_ -match '待定|TBD|最佳实践' }); "DESIGN.md 行数 $($l.Count)；缺失节 $($miss.Count)（要求 0）；AI 味行 $($bad.Count)（要求 0）"; if ($miss.Count -gt 0 -or $bad.Count -gt 0) { Write-Host '[FAIL] 设计文档自查未过'; exit 1 } else { Write-Host '[OK] 设计文档自查通过' }
```

**设计通过四证（缺一 = 设计未通过）：**
① DATA_DICT diff 每行都标了敏感度 D1~D4｜② APIS 每行都含错误码与鉴权列｜③ 组件影响清单已列出（含"待建行"标注）｜④ down 由人本地空跑通过，输出已贴回（无表结构 → ③ 证据回执第 4 项写 N/A，并在 `## ④ 状态回写` 的 `裁剪记录` 写依据）

**AI 味五签名红线（设计文档里出现任一条 = 设计未通过）：**
① 无出处的量化声明（"性能提升 10 倍""业界最佳实践"）｜② 占位内容当设计（`待定`、`TBD`、假人名品牌名、非 seed 节里的假数据）｜③ 装饰性话术（"赋能""闭环""一站式"）替代可测判据｜④ 没有取舍的"全都做"（把 Won't Have 悄悄挪回 Must）｜⑤ 照抄别的项目结构而不说明为什么适合本项目

**禁令：**
- 禁止只写 up 不写 down
- 禁止 agent 执行 SQL / 迁移（不可委托清单项）
- 禁止 seed 用真实个人信息
- 禁止把 L3 破坏性变更藏进普通迁移
- 禁止设计未获人批准就进 4-1
- 禁止跳过九节骨架的任意一节（缺节不是"以后再补"）
- 禁止动作 9 自评 <3 分仍进 ③ 回执
