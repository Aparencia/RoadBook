# 卡 4-1 · 分批编码（全档必走；批级知会 + 需求级 gate）
> 触发：2-2 需求范围获用户确认后（L 档先过 3-1 设计）｜ 产物：代码 + 分批提交 ｜ 下一张：4-2 代码审查（S 档：4-1 绿灯后直接进 4-3（跳过 4-2）；M/L 档：4-2 绿灯且用户放行后进 4-3）

---

## ① 开工确认

收到开工指令后，先回执以下九项再动手：

1. **任务复述与落点**：本次实现 SCOPE 的哪些 Must 项（逐条列出）；产物 = 代码 + 分批提交；下一张卡 = 4-2 代码审查（S 档：4-1 绿灯后直接进 4-3，跳过 4-2）。
2. **假设清单**：逐条写"我假设 X；若错则 Y 失效"——能从项目文件查到的不许写进假设，先去查。
3. **澄清问题（≤5 个，能删则删）**：只问 SCOPE.md / STATE.md 查不到、又决定实现走向的事；一个都没有就写"无"。
4. **起点锚点声明**：执行 `git rev-parse HEAD` 并原样回显哈希（这行哈希是审查 diff 和回滚的基准）。
5. **分批计划**：把 Must 项切成批次，每批 ≤300 行或 1 个 Must 项，列表回执。**批次接口契约**：每批写两行——`Consumes：用到哪一批的哪些确切签名（函数名/参数/返回类型）` / `Produces：后续批次依赖的函数名、参数与返回类型`；批间无共享接口 → 写一行 `批间无共享接口`。**批间接口预检**：开工前对每对 Consumes/Produces 出一行核对结果（一致 / 冲突 + 裁决），写进本批知会或 STATE.md；对不上的现在改，不带进编码。**派单粒度（先于并行判定）**：几件同形小事（同一处一行改动 / 同一个常量替换 / 同一个字段在各文件补齐）**并成一次派单**，不许多派——判据是这三问，任一为「是」才单独派：① 需要它自己的判断吗？② 需要它自己的测试吗？③ 需要它自己独立的审查面吗？三问全否 = 并成一次。**并行判定（按任务量机械判定，不许临场发挥）**：预估总改动 ≥500 行 且 能按 Files 域切出 ≥2 个互斥单元（**每单元 ≥250 行**）且 每单元有独立可验证判据 → 提出并行派单方案（固定五列表，每片一行五列：`片号 | Files（互斥声明）| 根因域（一句话，且证明与其它片不同根因）| 独立可验证判据（怎么单独验）| 期望产出（几行、含什么）`；**根因域一列填不出与其它片的区别 → 禁止拆片**；期望产出留空 → 派单作废）等用户一次性确认；不满足任一条 → 串行。**算式（把数算给人看）**：单元门槛 × 最少单元数 = 250 × 2 = 500 = 总改动下限 500（旧门槛 150 时 150 × 2 = 300 < 500，两个单元永远凑不到下限，故上调为 250）。
6. **引用检查清单原文**（逐字粘贴本卡 §② 的"每批必念六查" + "条件触发暂停清单"）。
7. **声明生成标准**：本次所有生成代码对照宪法 §11「代码生成硬标准」逐条自检——结构（≤500 行/**测试文件豁免至 ≤1000 行**/纯逻辑与副作用分离/依赖显式传入）、命名（业务术语一致/入参出参有类型契约/禁 any）、注释写 Why、防御（外部调用有超时和失败分支/禁空 catch）、核心逻辑纯函数、禁硬编码配置。
8. **基线记账（净增量账本的 0 点）**：回执三个基线数字——`git rev-parse --short HEAD` 的短哈希、`(git ls-files).Count` 的文件数、`git status --porcelain` 输出为空（工作树干净；`git diff --numstat` 对未跟踪的新文件是空输出，会漏判）。基线不干净 → 先问用户怎么办，不许在脏树上开账。
9. **教训检索（JIT）**：先赋值 `$kw = 'checkout'`（换成本任务涉及的模块或关键词），再跑 `Select-String -Path docs/lessons/*.md -Pattern $kw -List`（无该目录则声明"无历史教训"），命中则回执卡名 + 要点一行——这些是本模块的已知雷区，写代码时逐条对照。

并声明停顿口径（照这句话执行，不临场解释）：**S 档：三批连续写完只汇报一次（贴三批账本），等用户说"继续"再进 4-3；M/L 档：每批汇报后等用户说"继续"；触发条件触发暂停清单任一条 → 立即停下等裁决**。（**S 档免审**：4-1 绿灯后直接进 4-3，由 4-3 的 guardrail 兜底。）

## ② 执行

**第 0 步（禁止跳过）：记录起点锚点**

```powershell
$anchor = git rev-parse HEAD
```

把 `$anchor` 的输出写进 STATE.md 的 `起点锚点` 字段。丢了它 = 4-2 卡无法审 diff、出问题无法精确回滚。

**动作 1：写代码，按批次推进（并行车道见附则）**
- 每批只做计划里的一个批次。
- 落点规则：新文件放哪，先查 `docs/ARCHITECTURE.md` 的"新代码落点表"；要新建组件/模块，先查 `docs/registry/` 三件套——**已有近似物就复用，禁止平行新建**。
  ❌ 反例：找不到旧按钮组件 → 新建 `Button2.tsx`
  ✅ 正例：搜到 `PrimaryButton` 复用之；确实不适用 → 在回执里写"为何不用已有组件"再新建
- **TDD 红先行（M/L 档）**：新功能的第一条测试必须先跑出红——`<测试命令> <file>` 输出失败，且失败原因 = 该行为尚不存在；测试第一次跑就绿 = 你测的是既有行为，改测试，不是改代码；绿了才写实现。
  ❌ 反例：先写完 `retryOperation()` 再补测试 → 立即通过，等于没测
  ✅ 正例：先写 `expect(attempts).toBe(3)` → 红（`retryOperation is not defined`）→ 再写实现 → 绿
- **第一批落盘后**：把 check.ps1 的 `$STEPS` 从零依赖占位检查换成真实构建/测试命令（接入时先放占位，此处必须替换；不换 = 收尾仪式只验证文档格式，验证不到代码）。

**每批必念六查（念完，结果写进本批知会）**：① 只动了 SCOPE 涉及的文件吗（`git status` 逐文件核对）｜② 有没有顺手改 SCOPE 外的东西（发现就还原；想修就登记 `docs/TECH_DEBT.md`）｜③ 新建的每个文件都说明"为何不能用已有文件"了吗｜④ 依赖有变化吗（lockfile 变了单独说明；禁未请求的依赖升级）｜⑤ 碰到 Won't Have 清单里的功能了吗（碰到就停，那是越界）｜⑥ 本批每条要跑的命令都写了 `Expected：` 行吗（实际输出与 Expected 不一致 → 先归因：代码错回 6-2 根因分析；计划错走「自行裁决留痕」并继续——**禁止把输出改成通过**）。

**动作 2：每批提交 + 进度知会**
**本批开工第一件事**：`$prevBatch = git rev-parse HEAD`（= 上一批末提交；首批开工时等于起点锚点）——动作 3 的"本批分母"靠它，忘了记就只能伪造账本。
提交前：本批若触碰 UI/表/接口 → **当场更新 registry 对应行（COMPONENTS/DATA_DICT/APIS），随本批一起提交**。回写随批走，禁止攒到归档时凭回忆追赶。

```powershell
$batchFiles = @('src/a.ts','src/b.ts')   # 换成本批真实文件清单；禁止 git add -A / git add .
git add $batchFiles
$slug = 'checkout'; $what = '实现购物车结算接口'   # scope 短名 + 本批做了什么（一句话）
git commit -m "4-1 feat($slug): $what"
```

提交后发一行**进度知会**（批号 + 六查结果摘要 + registry 回写情况），随后按上面声明的停顿口径执行（S 档一次汇报；M/L 档等用户说"继续"）。

**批次完成行（固定格式，原文写进知会与 `STATE.md`）**：`本批 N：complete（提交 <prevBatch 短哈希7>..<HEAD 短哈希7>，测试：<命令原文> → <输出末行>）`；**测试/构建命令没跑或没通过 → 不写"完成"二字，只写"未完成 + 卡在哪"**。

**提交信息格式（全库统一）**：`<卡号> <type>(<scope>): <摘要>`——type ∈ feat/fix/docs/chore/style/refactor/test；卡号让 5-1 卡能按提交回溯批次（`git log --oneline` 里 `4-1 ` 开头的就是本任务的批次清单）。

提交前后跑**机械门禁**（零 token 检查，替代人工逐条核对六查的①④）：

```powershell
$anchor = (Select-String -Path STATE.md -Pattern '起点锚点\s*[:：]\s*([0-9a-fA-F]{7,40})').Matches[0].Groups[1].Value   # $anchor 从 STATE.md 的「起点锚点」字段读，不许手打
git rev-parse --verify "$anchor^{commit}"; if ($LASTEXITCODE -ne 0) { throw "锚点无效：停下问用户（禁止硬跑）" }
$scopeFiles = @('src/a.ts','src/b.ts')   # 换成 SCOPE 文件清单
powershell -NoProfile -File gate.ps1 -Anchor $anchor -ScopeFiles ($scopeFiles -join ',') -RepoRoot .
```

红（exit 1）→ 停下修（**行数超限、lockfile 变更也是红**）；黄（重命名条目、空变更清单）→ 随知会转述给用户，仍 exit 0。

**动作 3：净增量账本（每批提交后当场算，禁止攒到收尾凭回忆补）**
五个数字一次报全：**新增文件数 / 删除文件数 / 新增行 / 删除行 / 净行数**（净行数 = 新增行 − 删除行），并贴命令真实输出。**两行各有用途，分母不许混用**：**本批行**（分母 = 上一批末提交）判"本批改存量却没删东西"；**任务累计行**（分母 = 起点锚点）判整需求是否碰到范围蔓延触发线。

```powershell
$anchor = (Select-String -Path STATE.md -Pattern '起点锚点\s*[:：]\s*([0-9a-fA-F]{7,40})').Matches[0].Groups[1].Value
git rev-parse --verify "$anchor^{commit}"; if ($LASTEXITCODE -ne 0) { throw "起点锚点无效：停下问用户" }
$prev = 'a1b2c3d'   # 粘贴本批开工时 $prevBatch 的真值（首批 = $anchor），别照抄示例
git rev-parse --verify "$prev^{commit}"; if ($LASTEXITCODE -ne 0) { throw "上一批末提交无效：停下问用户" }
$s = git diff --numstat "$prev..HEAD" -- .; if (@($s).Count -eq 0) { throw "本批 numstat 空输出：核对 $prev..HEAD，禁止当成新增 0 行" }
$a=0;$d=0;$f=0;$b=0; foreach ($l in $s) { $p = $l -split "`t"; if ($p[0] -eq '-') { $b++; continue }; $a += [int]$p[0]; $d += [int]$p[1]; $f++ }
"本批 $prev..HEAD ｜文件 $f（二进制 $b）｜新增 $a 行｜删除 $d 行｜净 $($a-$d) 行"
if ($d -eq 0 -and $a -gt 50) { "红灯：改存量批次删除行 = 0（停下补删再提交）" }
$ns = git diff --name-status "$prev..HEAD" -- .; "本批新增文件 $(@($ns | Where-Object { $_ -like 'A*' }).Count)｜删除文件 $(@($ns | Where-Object { $_ -like 'D*' }).Count)"
$c = git diff --numstat "$anchor..HEAD" -- .; if (@($c).Count -eq 0) { throw "累计 numstat 空输出：停下问用户" }
$ca=0;$cd=0; foreach ($l in $c) { $p = $l -split "`t"; if ($p[0] -eq '-') { continue }; $ca += [int]$p[0]; $cd += [int]$p[1] }
"任务累计 $anchor..HEAD ｜新增 $ca 行｜删除 $cd 行｜净 $($ca-$cd) 行（范围蔓延触发线对照用）"
```

红灯判据（内联，不许解释性豁免）：**本批行"删除行 = 0 且新增行 > 50" → 红灯**，停下补删再提交；纯新建文件批次豁免，但回执必须写一句"本批为纯新增"。`$prev..HEAD` 覆盖本批全部提交；只看 `HEAD~1` 会漏掉本批前面几笔，等于伪造账本。

**动作 4：取代即删除 + 并行态登记簿**
规则一句话：**新实现落地的那一批，必须删掉被取代的旧实现**（旧文件/旧函数/旧分支/旧常量一起走）。
做不到（灰度/回滚/兼容契约）→ 必须在 `STATE.md` 的"并行态登记簿"里登记，列固定：
`并行态 | 旧实现 | 新实现 | 删除条件（可判定） | 到期 | 登记批次`
只有三种合法保留理由（没有第四种，其余一律删除）：
① **灰度/回滚** —— 必须带期限（到哪个批次、什么条件到期）
② **对外兼容契约** —— 必须带弃用期
③ **证据留存** —— 答案是 git 历史，工作树不许留第二份；`.bak`、`旧版/`、`副本 2` 是**唯一示例出处**（其余卡不再重复举例）
❌ 反例：新建 `xxx_v2.ts` 实现一遍，旧 `xxx.ts` 留着"以防万一"
✅ 正例：同批删旧 + 回执贴删除行证据 + 并行态登记簿无新增行

**动作 5：文件登记与膨胀（新增文件不是可选项）**
新增任何文件（含脚本/文档/测试）→ 必须在本批内于 `docs/registry/COMPONENTS.md` 登记 `路径 + 用途 + 归属批次`，随本批提交。
回执必须贴 `powershell -NoProfile -File orphans.ps1` 的汇总行（完整格式：`孤儿 X 项｜零引用导出 Y 项｜文档幽灵 Z 项｜反向幽灵 W 项｜未登记 V 项｜未跟踪 U 项｜读取失败 R 项｜文件数 N`；**未跟踪 U 或读取失败 R 非 0 时退出码为 1**——先 `git add` 再复跑，别把"清单不完整"当孤儿）。
红灯：本批新增文件 > 20 个 → 停下先合并，或说明为什么必须拆这么多（说明写进本批知会）。

**条件触发暂停清单（出现任一条，立即停下等用户，禁止"做完这批再说"）**：① 触碰红线域（认证 / 支付 / 删除数据）｜② 停问规则触发（同一错误第二次出现）｜③ 累计变更行数 > `预估改动行数` × 1.5（`预估改动行数` 是 SCOPE 里的字段名，逐字引用；范围蔓延的量化信号）｜④ 需要新增依赖或修改共享配置｜⑤ 触及 Won't Have 清单（越界）。**自行裁决留痕（没停下问人的判断，每条留一行）**：格式固定 `裁决：【决定了什么】—【依据】—【错了的代价】`，写进本批知会与 `STATE.md` 未决问题；代价 ≥ 半天返工的，回执里点名请用户复核。纯机械动作（改名 / 格式化）不写；一条 ≤1 行。

**禁令（违反 = 本批作废）**：禁止 `git add -A` / `git add .`；禁止升依赖、改全局配置、动宪法（AGENTS.md）；禁止"顺手重构"（看到别处有问题 → 登记 `docs/TECH_DEBT.md`，不许顺手修）；禁止跳过条件触发暂停（"就快写完了"不是理由）；禁止新实现落地却把被取代的旧实现留在树里（未登记进并行态登记簿 = 违规）；禁止在工作树里留第二份证据副本（示例见动作 4 的唯一示例出处；证据在 git 历史里）；禁止先写实现后补测试——补出来的测试立即全绿，证明不了任何事；「留着当参考」也算违规：已写的实现必须丢弃（未提交产物），并在 STATE.md 申报丢弃了什么。

**并行车道附则（① 第 5 项判定通过且用户确认派单后才可开）：**
- **先判相关性，再判文件域**：两片即使 Files 完全不重叠，只要**共享同一契约**（一片改被调方、另一片改调用方）、**共享同一可观察行为**（同一验收标准）、或**根因是同一个**，禁止拆成两片——并成一个单元。判据一句话：「修好一片，另一片的问题会自动消失吗？」会 → 合并。
- **还不知道怎么改的，不许开并行**：并行车道只在「每一片都已经知道要改什么」时开；处于「先查明坏在哪」阶段 → 串行，或按 6-2 卡先做根因分析。
- 每单元开 **git worktree**（独立目录独立分支）各自实施+提交；**多单元直写同一工作树 = 禁止**（防互踩，评估过不采纳）
- 开单元工作区前先跑两条探测命令并把原文贴进开工回执：`git rev-parse --git-dir` 与 `git rev-parse --git-common-dir`——两者输出**不一致**、且 `git rev-parse --show-superproject-working-tree` **无输出** = 已经在隔离工作区里 → **禁止再开一层**，直接在现有工作区里做；两者输出一致 = 普通仓库，可开。
- 开之前必须 `git check-ignore -q .worktrees`（**无输出 = 未被忽略**）→ 未被忽略时先把 `.worktrees/` 写进 `.gitignore` 并**单独一个提交**，再开工作区。回执里贴 `git check-ignore -v .worktrees` 的真实输出。理由写死：未忽略就开 = 整棵工作树会被提交进仓库。
- 共享文件（registry / STATE / 宪法 / CHANGELOG）**只由主 agent 写**——单元发现需要改共享文件 → 停下报主 agent
- 主 agent 依序合并各单元分支，冲突 → STOP 问人；**合并后先做返回四步核验**：① 逐份读各单元回执（不读汇总）② 核对有没有两片碰了同一文件 ③ 全量跑一次 guardrail ④ **抽查 diff**——子 agent 会犯系统性错误（同一错误模型会在每一片重复），「全量绿」不替代人工点开 diff。四步做完才走 4-2（一次审全部）。
- 合并前先确认基分支：贴 `git log --oneline <基分支>..<单元分支>` 的输出，并问一句"这个单元分支是从 <基分支> 分出来的，对吗？"——**合并到错的基分支，撤销代价很高**；未得到确认不许合并。
- 每合并一个单元分支，**就在合并结果上重跑一次全量测试**（命令口径唯一：`AGENTS.md` §10 与 `check.ps1` 顶部 `$STEPS`），贴命令原文 + 完整输出。不通过 → 停下，保留单元分支与工作区原地不动并排查（此时还没推送，合并是本地的、可退）；通过才继续合并下一个。**"绿"只证明它跑过的那个树——本会话早先的绿灯不算数。**
- 并发怎么发生：并行片必须在**同一条指令里一次性派完**（一次派一片 = 串行）。派完即等回执，不轮询、不催单。
