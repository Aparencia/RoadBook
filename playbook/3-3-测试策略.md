## ② 执行

**动作 1：金字塔三层分配（表格化；比例写死一个数，防"全写端到端"）**

| 层 | 覆盖什么 | 大致比例 | 跑一次多久 | 谁写 |
| :-- | :-- | :-: | :-- | :-- |
| 单元 | 纯函数与规则：金额计算、状态机、校验器（无网络、无数据库） | ~70% | 秒级 | agent 每批同写 |
| 集成 | 跨边界：API 路由 + 数据库读写 + 第三方 mock（含错误分支） | ~20% | 分钟级 | agent 每批同写 |
| 端到端 | 用户真走一遍的关键路径（浏览器或命令行全链路） | ~10% | 分钟级 | 每任务 1–3 条 |

任一层为 0，必须在"哪些不测"里写理由。
❌ 反例："以单元测试为主，端到端适当覆盖"（无数字、无法验收）
✅ 正例："单元 ~70%（约 40 条，<10 s 跑完）；集成 ~20%（12 条）；端到端 3 条（登录 → 下单 → 退款）"

每条单元测试必须能说出一个会让它变红的生产改动；说不出、或只有"常量值/提示文案/私有结构"这种有意改动能让它红的 → 重写为对**依赖该决策的行为**的断言（例：不测 `MAX_RETRIES === 5`，测"失败调用被重试 5 次且第 6 次不再发生"）。

**动作 2：关键路径清单（每条 = 入口 → 动作 → 必须成立的结果）**
从 SCOPE.md 的验收标准与 NFR.md 的阈值各抽条目，一条不漏。
❌ 反例："下单流程要测"（无入口、无预期，跑起来也不知道对错）
✅ 正例："`POST /orders` 带合法商品 → 201，且数据库新增 1 条订单、库存 -1"
有 3-2 时至少 1 条越权拒绝用例（拿 A 的身份访问 B 的资源，必须被拒）；有 NFR 阈值时至少 1 条阈值用例（如 P95 ≤ 800 ms 的计时）。

**动作 3：覆盖率门槛（两行分开写，禁止合并）**

| 范围 | 门槛 | 怎么量 | 不达标怎么办 |
| :-- | :-- | :-- | :-- |
| 新增代码 | 行覆盖 ≥ 80%，分支 ≥ 70% | 测试运行器 `--coverage` 报告 | 补测试；确属脚手架 → 写进"哪些不测"并排除 |
| 全仓 | 行覆盖 ≥ 60%，只升不降 | 同上，与上次报告对比 | 降了判红，先补回再进 4-3 |

数字按项目实际改；本项目没有覆盖率工具时，改用量化替代写进 TESTPLAN.md："关键路径 100% 有用例 + 每个判据做一次变异体证伪"。
❌ 反例："覆盖率达标即可"（达标是谁定的？）
✅ 正例："新增 ≥80%，全仓 ≥60%；低于就补，禁止写'部分覆盖'放行"

**动作 4：夹具与测试数据策略**
- 夹具来源三选一：工厂函数（随机但可复现，固定随机种子）／手写静态 JSON／脱敏快照。
- **禁止使用生产数据**（含导出的真实用户表、真实手机号、真实订单）；需要真实数据量级时，用脚本生成等价规模数据。
- 数据落点 `tests/fixtures/`，随仓库提交且不含个人信息；每条数据要能被一条命令重置。
- 自查命令：
```powershell
Select-String -Path 'tests/fixtures/*' -Pattern '\d{11}|@(qq|163|gmail)\.com' | Select-Object -First 5
```
命中 = 疑似真实手机号／邮箱，逐条换成生成数据。

**动作 5："哪些不测"显式列出（三列表：不测什么／为什么／替代手段）**

| 不测的东西 | 理由 | 替代手段 |
| :-- | :-- | :-- |
| 第三方真实扣款 | 需要真钱与真账号 | 沙箱 + mock 回调；上线前人工小额实测 |
| 像素级视觉差异 | 没有设计稿基线 | 人工目检，写进行为验收清单 |
| 老版本浏览器 | 用户群不用 | 不承诺支持，写进项目 README |

**动作 6：本策略 = 4-3 验证分级的判据（取代"1~2 条测试"的经验值）**
- M 档：按本卡关键路径清单逐条跑 + 新增代码覆盖率达标。
- L 档：再加负面测试与越权拒绝用例（不许零测试）。
- TESTPLAN.md 末尾写"4-3 要跑的命令"一节，一行一条，4-3 直接复制执行。

**动作 7：接缝先约定 + 点名两种反模式（派单给实现者之前定，写进 TESTPLAN.md）**
派单给实现者之前，先与用户/审查者**接缝先约定**：哪个函数、哪个接口允许被替换或打桩，逐个点名写进 TESTPLAN.md——接缝不写清楚，实现者会自己挑一个，到 4-2 审查时才发现替换不进去。
两种反模式逐条点名（写在 TESTPLAN.md 的"哪些不测"邻近处，收工前逐条自查）：
- **同义反复测试**：断言重抄实现（把实现改坏，测试照样绿）。判据一句话：这条测试说得出"改哪一行生产代码会让它变红"吗？说不出 → 就是同义反复，重写为对**依赖该决策的行为**的断言。
- **横向切片**：按层切任务（先做完整个数据层、再做整个接口层），做完整层都不产生可运行行为。判据一句话：每个切片必须纵向贯穿到可运行——切完就能演示一条用户行为；做不到 → 切片方式作废，重切。
❌ 反例：`expect(add(1, 2)).toBe(1 + 2)`（断言重抄实现，改坏 add 也是绿的）
✅ 正例：`expect(cartTotal(items)).toBe(1980)`（预期金额写死，改坏计算就红）

另写明：**重构不属于这个循环**——测试-实现-重构里的"重构"是就地小步（同一批里把刚写的代码收拾干净），不是另开一批；要成规模地重构，另立任务另走流程。

**禁令：**
- 禁止用生产数据做夹具（"脱敏后再用"也不行——脱敏不彻底就是泄露）
- 禁止写"不测"却不给理由；"环境不具备"不是理由，去找替代手段
- 禁止只报覆盖率数字不贴报告输出（数字必须有命令输出兜底）
- 禁止事后放宽策略：策略变更必须同轮改 TESTPLAN.md 并在回执里写明原因，不许口头放宽
- 禁止用固定 `sleep`／固定延时等待异步结果：等待必须写成"轮询条件 + 明确超时"（超时报文里带条件描述与毫秒数），轮询间隔与超时值必须注释写出依据；用例偶发失败时先定位不确定性来源，禁止靠调大延时让它变绿。
