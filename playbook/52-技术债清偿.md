## ① 开工确认

1. **批次类型判定（先定类型再动手）**：
   - **T 批（债清偿批）**：按台账逐条清，范围 = 用户挑定的条数
   - **P 批（清理批）**：只允许删除 / 合并 / 重命名 / 收敛，**不允许新增功能**；减少目标必须开工写死（见 §② P1），没写目标 = 不算 P 批
   - P 批触发（任一）：每 3–5 个功能批次后强制一次 ｜ 43 卡体检触发 ｜ 台账"腐化类"条目 ≥5 条
2. **台账视图**：读 `docs/TECH_DEBT.md`，输出优先级视图（按 来源严重度/影响面/躺了多久 排序，每条一行），并把"腐化类"条目单列。
3. **清偿建议**：从视图里挑"性价比最高"的 1~3 条（影响大/改动小优先），说明理由。
4. **引用检查清单原文**（逐字粘贴"清偿三规则"；P 批加贴"P 批次四步"）。

等用户挑定清哪几条（P 批：等用户确认减少目标），再动手。

## ② 执行

**清偿三规则：**

**规则 1：按性质路由，别硬修**
- 代码债 → 按 23 分批编码的纪律走（起点锚点/分批/合规五查），每条债一个任务
- 文档债（registry 缺行/RUNBOOK 过期）→ 直接修，一次清完
- "无法复现"类 known-issue → 不许清，只能续期或降级为"观察中"

**规则 2：关闭必须附证据**
```powershell
git rev-parse HEAD   # 修完把哈希填进台账"偿还证据"列
```
❌ 反例：状态改 closed，证据列写"已修复"（空口无凭）
✅ 正例：closed，证据=`commit a1b2c3d; tests/test_export_limit.py`

**规则 3：清债也是任务，范围照样锁**
- 修债过程中发现新问题 → 登记新 TD 条目，不许顺手扩修
- 债条目描述与实际代码对不上（债本身过时了）→ 改为 closed + 证据写"复核确认已不存在：文件 X 现状"

**P 批次（清理批）四步——只删 / 只并 / 只收，不许新增功能：**

**P1 减少目标（开工写死，收尾核对）**
```powershell
git diff --numstat <起点锚点>..HEAD
```
逐行 = 增 / 删 / 文件；把"删"列求和对比开工写死的目标（如"净减 ≥200 行 或 ≥3 个文件"）。未达标 = 本批不算完成（可续批，**不许改目标**）。

**P2 安全删除（母版教训：递归删除穿透 junction 曾造成事故）**
- 批量删除**必须先 dry-run 输出清单**（先只列路径不删，或 `-WhatIf`），并**路径白名单化**（只删白名单内的精确路径）
- 清单贴进回执，**让人过一眼再删**——未确认前一行都不执行
- ❌ 反例：`Remove-Item -Recurse` 直接作用于未经确认的目录（一次穿透 = 不可逆事故）
- ✅ 正例：先出"待删 37 个文件"清单 → 人确认 → 逐条删 → 回执贴删除行数 / 文件数

**P3 收敛动作白名单**：删死代码与孤儿文件 / 合并重复实现 / 重命名到统一术语 / 收敛配置与目录。**新增功能、升依赖、改架构一律出界**（那是专门任务）。

**P4 验收四件齐**
1. 减少目标达成（P1 的 numstat 对比原文）
2. `powershell -File check.ps1` 退出码 0
3. 回归验证通过（25 卡 / 32 卡）
4. `orphans.ps1` 三张清单在回执里贴出

❌ 反例：把 P 批次做成"顺手重构 + 加新功能"（等于没清，还平白引入新面）

**禁令：**
- 禁止一次清超过用户挑定的条数
- 禁止"顺便把整个台账都关了"——每条关闭都要独立证据
- 禁止清偿还债时升依赖/改架构（那是专门任务）
- 禁止 P 批次不写减少目标就开工（"边清边看"不是目标）
- 禁止无 dry-run 清单、无路径白名单的批量删除（递归删除穿透 junction 是真实事故）
