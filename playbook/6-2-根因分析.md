# 卡 6-2 · 根因分析（全档必走）
> 触发：Bug/报错/行为不对 ｜ 产物：docs/specs/<日期>_<slug>/RCA.md ｜ 下一张：6-3 修复（P0 先止血：回滚优先于修复）

---

## ① 开工确认

收到 Bug 报告后，先回执以下六项：

1. **人话复述与落点**：哪个功能出了什么问题（一句话）；产物 = `docs/specs/<日期>_<slug>/RCA.md`；下一张卡 = 6-3 修复。
2. **假设清单**：逐条写"我假设 X；若错则 Y 失效"——能从代码/STATE.md 查到的不许写进假设，先去查。
3. **澄清问题（≤5 个，能删则删）**：只问用户才知道、又决定定位方向的事；一个都没有就写"无"。
4. **诊断四问**（用户答不出就陪他找，不许跳过直接猜原因）：
   - 预期行为是什么？
   - 实际行为是什么？
   - 报错原文（完整粘贴，一张截图一行字都不许省）
   - 最近一次改动（大概时间/内容；从 STATE.md 的"最近完成"辅助回忆）
5. **复现方案**：提出怎么复现（哪个页面/什么操作/什么数据）。
6. **引用检查清单原文**（逐字粘贴本卡 §② 的"五问法对照"）。

---

## ② 执行

**动作 1：人工复现（禁止跳过）**
- 用户亲自复现，或用户操作、agent 同屏看输出。
- agent 不许"根据代码推断已复现"。
  ❌ 反例："从代码看这里必然报错，无需复现"
  ✅ 正例："请在登录后点击'导出'按钮，我同时在终端看日志——你点了吗？看到了什么？"
- 复现不出来 → 登记 `docs/TECH_DEBT.md`（known-issue），给出收集信息方案（如截图+操作步骤+时间点），本卡结束。

**动作 2：定位（按序试，命中最前面的就停）**
1. 报错串里的文件/模块名 → 先赋值再搜：`$kw = '报错关键字'; Select-String -Path src -Pattern $kw -Recurse | Select-Object Path,LineNumber`
2. 界面文案 → 全仓库搜文案（同上，换成文案关键字）
3. 查 `docs/registry/COMPONENTS.md` 的"人话标识"列反查程序名
4. 查 `docs/lessons/` 教训卡是否同症状（有 → 先按旧卡修法试，成功则在旧卡上更新「最近确认」字段 = 日期 + 本次确认的证据；**旧卡没有这个字段 → 先补字段再更新**，不许因为没字段就跳过更新）；**若命中已有教训卡（同症状第二次发生）→ 修复完成后必须起草"升格提案"：把这条教训从知识升格为规则（写进宪法禁令或对应流程卡的检查项，落到具体文件+具体条目），交用户裁决——踩两次的坑，第三次还会来**

**动作 3：五问法对照 —— ≥3 层（问到底，不许一层就停）**

```text
❌ 反例（1 层就停）：
   为什么白屏？→ 因为 data 是 undefined。（完）
✅ 正例（4 层到底）：
   为什么白屏？→ data 是 undefined
   为什么是 undefined？→ 接口返回结构变了
   为什么结构变了？→ 上周改接口的人不知道前端在用旧字段
   为什么会不知道？→ docs/registry/APIS.md 里没登记这个接口
   → 根因：接口未登记（修 APIS 登记 + 修代码，两个都要做）
```

**动作 4：Bug 定级（判据内联，不确定按 P2）**
- P0 系统崩溃/数据丢失/安全漏洞 → 先止血：回滚优先于修复（步骤在 docs/RUNBOOK.md 回滚节）
- P1 核心功能不可用 → 立即修复
- P2 边缘功能报错/体验不佳 → 正常修复
- P3 拼写/样式/非关键 → 不进修复流程，登记 TECH_DEBT.md 攒批，本卡结束

**动作 5：写 `docs/specs/<日期>_<slug>/RCA.md`**：现象/复现步骤/根因（≥3 层）/影响面/修复方案建议。路径里的 `<slug>` 与卡头、STATE.md 的 `当前任务` 用同一个 slug，不许一处叫 bug 名一处叫 slug。
