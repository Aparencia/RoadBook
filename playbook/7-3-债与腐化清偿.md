# 卡 7-3 · 债与腐化清偿（技术债 T 批 / 清理 P 批）
> 触发：用户说"还债/清技术债/清理一下"，或每 3–5 个功能批次后强制一次清理批 ｜ 产物：清偿提交 + 台账关闭 ｜ 下一张：5-1 归档

---

## ① 开工确认

1. **批次类型判定（先定类型再动手）**：
   - **T 批（债清偿批）**：按台账逐条清，范围 = 用户挑定的条数
   - **P 批（清理批）**：只允许删除 / 合并 / 重命名 / 收敛，**不允许新增功能**；减少目标必须开工写死（见 §② P1），没写目标 = 不算 P 批
   - P 批触发（任一）：每 3–5 个功能批次后强制一次 ｜ 6-6 卡体检触发 ｜ 台账里描述含"腐化/重复/上帝类"关键词的条目 ≥5 条
2. **假设清单**：你替用户做的 3~5 条默认假设（例："这些债没有隐藏依赖""待删文件无外部引用"），每条注明验证方式。
3. **澄清问题（≤5 个，能省则省）**：默认三问——本轮清几条？清哪几条（让人挑）？要不要顺带开一次 P 批？台账与代码里查得到的禁止问人。
4. **台账视图**：读 `docs/TECH_DEBT.md`，输出优先级视图（按 来源严重度/影响面/躺了多久 排序，每条一行），并把描述含上述关键词的条目单列——筛法：描述列含"腐化/重复/上帝类"关键词，用下面命令拉清单：
```powershell
Select-String -Path docs/TECH_DEBT.md -Pattern '腐化|重复|上帝类'
```
5. **清偿建议**：从视图里挑"性价比最高"的 1~3 条（影响大/改动小优先），说明理由。
6. **引用检查清单原文**（逐字粘贴本卡 §② 的"清偿三规则"；P 批加贴"P 批次四步"）。

等用户挑定清哪几条（P 批：等用户确认减少目标），再动手。

## ② 执行

**清偿三规则：**

**规则 1：按性质路由，别硬修**
- 代码债 → 按 4-1 分批编码的纪律走（内联三条：① 开工记起点锚点 `git rev-parse --short HEAD`；② 每批一次提交、批间 `git status --short` 无输出；③ 每批按 4-1 的"每批必念六查"逐条过，结果写进回执），每条债一个任务
- 文档债（registry 缺行/RUNBOOK 过期）→ 直接修，一次清完
- "无法复现"类 known-issue → 不许清，只能续期或降级为"观察中"

**规则 2：关闭必须附证据**
```powershell
git rev-parse HEAD   # 修完把哈希填进台账"偿还证据"列
```
❌ 反例：状态改 closed，证据列写"已修复"（空口无凭）
✅ 正例：closed，证据=`commit a1b2c3d; tests/test_export_limit.py`

**规则 3：清债也是任务，范围照样锁**
- 修债过程中发现新问题 → 登记新 TD 条目，不许顺手扩修
- 债条目描述与实际代码对不上（债本身过时了）→ 改为 closed + 证据写"复核确认已不存在：文件 X 现状"

**P 批次（清理批）四步——只删 / 只并 / 只收，不许新增功能：**

**P1 减少目标（开工写死，收尾核对）**
```powershell
$anchor = 'abc1234'        # 起点锚点，从 STATE.md 读
git diff --numstat "$anchor..HEAD"
```
逐行 = 增 / 删 / 文件；把"删"列求和对比开工写死的减少目标。**硬阈值（开工写死，不许中途改）：净减 ≥200 行 或 ≥3 个文件**；未达标 = 本批不算完成（可续批，但目标不许改）。

**P2 安全删除（母版教训：递归删除穿透 junction 曾造成事故）**
- **删之前先过六问（Chesterton's Fence：答不出就不许删）**：① 它负责什么 ② 谁调用它（贴搜索命中行）③ 它调用谁 ④ 为何写成这样（贴注释 / 提交信息原文）⑤ 有无外部使用者、数据格式或兼容性锁死它 ⑥ `git blame -L 1,40 -- src/export/rate_limit.py` 与 `git log --oneline -5 -- src/export` 说了什么——答不出的那条先查清再动；"看着没用"不是删除理由
- 批量删除**必须先 dry-run 输出清单**（先只列路径不删，或 `-WhatIf`），并**路径白名单化**（只删白名单内的精确路径）
- 清单贴进回执，**让人过一眼再删**——未确认前一行都不执行
- ❌ 反例：`Remove-Item -Recurse` 直接作用于未经确认的目录（一次穿透 = 不可逆事故）
- ✅ 正例：先出"待删 37 个文件"清单 → 人确认 → 逐条删 → 回执贴删除行数 / 文件数

**P3 收敛动作白名单**：删死代码与孤儿文件 / 合并重复实现 / 重命名到统一术语 / 收敛配置与目录。**新增功能、升依赖、改架构一律出界**（那是专门任务）。

**P4 验收四件齐**
1. 减少目标达成（P1 的 numstat 对比原文）
2. `powershell -NoProfile -File check.ps1` 退出码 0
3. 回归验证通过（4-3 卡 / 6-4 卡）
4. `powershell -NoProfile -File orphans.ps1` 的**五张清单**（孤儿 / 零引用导出 / 文档幽灵 / 反向幽灵 / 未登记）汇总行原文贴进回执

❌ 反例：回执只写一句"orphans.ps1 跑过了，没问题"（五张清单一张没贴 = 没验）
✅ 正例：贴汇总行原文 + 三类处置计数（删除 x / 登记 TD x / 补登记 x），按去重后条目数相加 = 汇总行五类计数之和

❌ 反例：把 P 批次做成"顺手重构 + 加新功能"（等于没清，还平白引入新面）

**禁令：**
- 禁止一次清超过用户挑定的条数
- 禁止"顺便把整个台账都关了"——每条关闭都要独立证据
- 禁止清偿还债时升依赖/改架构（那是专门任务）
- 禁止 P 批次不写减少目标就开工（"边清边看"不是目标）
- 禁止无 dry-run 清单、无路径白名单的批量删除（递归删除穿透 junction 是真实事故）

## ③ 证据回执

1. 本轮清偿清单：TD 编号 → 结果（closed+证据 / 降级原因 / 改期）
2. 每个 commit 哈希
3. 台账文件当前状态摘要（open/closed 计数）
4. P 批：`git diff --numstat` 汇总（净增/净减行数 + 文件数 vs 减少目标）+ dry-run 删除清单 + `orphans.ps1` 五张清单的汇总行原文

## ④ 状态回写

**顺序铁律：先回写状态 → 再提交 → 再复跑 check.ps1 取 0。**

更新 STATE.md：`当前任务` 清空；`下一步` = 5-1 归档；`未决问题` = 改期条目的原因。
P 批额外：把本轮清掉的并行态条目从"并行态登记簿"划掉；到期未清的写回表内（留给下一轮 P 批）。

然后提交与复跑（台账关闭、删除清单、STATE.md 必须在同一次提交里）：
```powershell
$files = @('docs/TECH_DEBT.md', 'STATE.md')   # 再把本次改动的代码/文档文件逐个补进来
git add $files
git commit -m "7-3 chore(debt): 关闭 TD-00x 并同步台账"
powershell -NoProfile -File check.ps1
```
（禁止 `git add -A` / `git add .`；提交哈希回填 §③ 第 2 项。）
