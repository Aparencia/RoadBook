## ② 执行

**动作 1：备份清单（五列全填，缺一列 = 出事时不知道该恢复什么）**

| 备份对象（具体到文件/表/桶路径） | 频率 | 存放位置（写全路径或远端口令名） | 保留期 | 是否加密 |
| :--- | :--- | :--- | :--- | :-: |
| 例：`data/app.db` | 每日 03:00 | 例：`D:/backup/app/` + 异地一份 | 30 天 | 是 |
| 例：`.env`（密钥另存于密码库） | 变更时 | 例：密码库条目名 | 长期 | 是 |
| 例：用户上传目录 `data/uploads/` | 每日 03:00 | 例：对象存储桶名 | 90 天 | 否（内容本身非敏感） |

- 对象要**具体**：写"整个项目"= 没写；按 `docs/registry/DATA_DICT.md` 逐表过一遍，别漏掉新加的表/字段
- 保留期要写数字（不是"长期保留"）；加密与否逐条写明，不加密的要写理由
- 备份任务必须有**失败可见性**：备份没跑成功要有告警或日志能看出来（静默失败的备份 = 没有备份）

**动作 2：恢复演练（真跑一次，不是 `ls` 看文件在不在）**
```powershell
# 第 0 步：先在项目根取版本基线 —— doctor.ps1 只认项目根的 .tool-versions，演练目录里没有它
Set-Location D:/project/app
powershell -NoProfile -File doctor.ps1
# 第 1 步：取回最近一次备份并恢复到与生产隔离的演练目录（演练目录里不跑 doctor.ps1）
New-Item -ItemType Directory -Force -Path D:/restore-drill/2026-01-01 | Out-Null
Copy-Item D:/backup/app/app.db D:/restore-drill/2026-01-01/app.db
Set-Location D:/restore-drill/2026-01-01
```
三步缺一不可，每步贴真实输出：
1. **取回**：从存放位置真的取回一份（不是复制本机现有文件冒充）
2. **恢复**：按 `docs/RUNBOOK.md` 的恢复步骤恢复到一个**与生产隔离**的环境
3. **验证**：恢复后数据真的能用——按 `docs/registry/DATA_DICT.md` 至少核对两条具体数据（例：最新一条记录的时间戳与条数）；核不上 = 恢复失败，不是"大概可以"。要在演练目录里跑 `doctor.ps1`，先把项目根的 `.tool-versions` 一并复制进去，否则用等价自检（起服务 + 查数据）

- ❌ 反例：在空演练目录里直接 `powershell -NoProfile -File doctor.ps1` → 报"缺 .tool-versions"（它只认项目根；这是跑错地方，不是演练失败）
- ❌ 反例：`Test-Path D:/backup/app/app.db` 返回 `True` → 宣布"恢复能力已验证"（只证明文件在，不证明能恢复）
- ✅ 正例：先在项目根跑出 doctor 基线（退出码 0），再在演练目录里放一份 `.tool-versions` 复跑通过 → 两条输出都贴进回执
- ✅ 正例：恢复出来的库能启服务、能查到关键表的最新记录、条数与备份前一致 → 贴上这些读数

**动作 3：RTO / RPO 实测（估的也必须标明是估的）**
- **RTO（恢复到可用要多久）**：从"决定恢复"到"验证通过"的实测耗时（看表计时，写分钟数）
- **RPO（最多丢多少数据）**：按备份频率算——每日一备 = 最坏丢 24 小时数据；写清依据
- 给不出实测的照此写真实值：`估：45 分钟（依据：库 2.3GB、每日一备，未实测）`，**不许留空，也不许把估的写成实测的**
- 拿实测数字对照业务能接受的上限（① 开工确认的澄清答案：多久算"恢复到可用"、能接受丢多少数据）：超出 → 停下报用户，不许自行接受

**动作 4：演练记录（格式固定 + 有效期判据）**
`docs/RUNBOOK.md`「备份与恢复演练」节按此格式留一行（示例）：
`演练日期：2026-01-01 ｜ 对象：app.db(全表) ｜ 取回：成功 ｜ 恢复耗时：6 分钟 ｜ 验证：users 表 128 条与备份前一致 ｜ RTO 实测 8 分钟 ｜ RPO 24 小时（每日一备）｜ 下次到期：2026-04-01`
- **有效期 90 天**：超过下次到期日仍未再演练 → **红灯**（演练记录过期 = 备份能力不可信；这条红灯由流程体检项承接：体检读 `docs/RUNBOOK.md`「备份与恢复演练」节的"下次到期"字段，过期即报红灯并排入下一轮）
- 改过数据结构（新增表/字段/迁移）→ 上次演练记录立即失效，必须重跑本卡（旧记录不覆盖新结构）

**动作 5：两侧都要验证（"备份成功 ≠ 可恢复"）**
- 备份侧：最近一次备份的**成功**证据（任务日志或备份文件时间戳，贴输出）
- 恢复侧：本次演练的**成功**证据（动作 2 三步输出）
- 只有一侧 = 只验证了一半，回执里必须把缺的那侧写成"未验证"，不许合并成"备份链路正常"

**动作 6：记录落点与过期承接（写进文件，别靠记忆）**
- 演练记录写进 `docs/RUNBOOK.md`「备份与恢复演练」节的**"下次到期"字段**（格式见动作 4）——这是过期检查**唯一**的读取点
- 同批把"下次到期日"登记到 `STATE.md` 的 `未决问题`（写"演练下次到期 YYYY-MM-DD"）；归档收尾逐条核对这一栏，本次演练完就清掉该条并写明清除理由
- 90 天有效期的红灯由**流程体检项**承接（读 `docs/RUNBOOK.md` 的"下次到期"字段）：过期 → 体检报红灯并排入下一轮

**禁令（违反任一条 = 本轮输出作废）：**
- 禁止用 `ls` / `Test-Path` / "备份文件在" 代替恢复演练（本卡第一条红线）
- 禁止在生产环境做恢复演练（隔离环境；生产数据只读，且不得写回生产）
- 禁止把未实测的 RTO/RPO 写成实测（估的必须标"估 + 依据"）
- 禁止跳过验证步骤（恢复出来了但没核对数据 = 没验证）
- 禁止恢复演练时把生产密钥/真实个人信息带到演练记录里（记录只写对象与条数，不写内容）
