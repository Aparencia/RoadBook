# 卡 7-2 · 依赖升级
> 触发：需要升级依赖（用户要求或安全补丁） ｜ 产物：升级提交 + 兼容性结论 ｜ 下一张：5-1 归档
> 过程域：IMP, RISK

---

## ① 开工确认

1. **升级动机三选一**（前两者才值得动手，"主动追新"要劝退）：
   - 安全补丁（有 CVE/漏洞通报）
   - 新功能需要（某个 Must 依赖新版本 API）
   - 主动追新（❌ 默认拒绝：没有收益只有回归风险）
2. **假设清单**：你替用户做的 3~5 条默认假设（例："本次只动这一个包""不跨大版本"），每条注明验证方式。
3. **澄清问题（≤5 个，能省则省）**：默认三问——升到哪个**具体版本号**（不接受"最新"）？能否接受 breaking change？回滚窗口留多长？`.tool-versions` 与 lockfile 里查得到的禁止问人。
4. **影响面预告**：将用 `Select-String` 核对当前依赖被谁用（含 src 之外的 test/配置目录）。
5. **引用检查清单原文**（逐字粘贴本卡 §② 的"升级四查"）。
6. 并声明：产物落点 = 升级提交（lockfile 与代码适配分开两次）+ 兼容性结论；下一张卡是 5-1（归档）。

---

## ② 执行

**前置：STACK DETECTED（先回执，再谈升级）**
```powershell
git ls-files -- 'package.json' 'pnpm-lock.yaml' 'package-lock.json' '.tool-versions' 'pyproject.toml' 'requirements*.txt' 'Cargo.toml' 'go.mod'
```
Expected：逐个打印真实存在的清单文件（本仓实测 2 行：`.tool-versions`、`package.json`）—— 不存在的不打印也不报错；空输出 = 走错目录，或本仓库没有可识别的栈。
从命令输出里照抄一行回执：`STACK DETECTED：<工具> <确切版本>（来源：<命令>）`——版本号只认命令输出与 lockfile，不认记忆。
**来源纪律（三查）**：① 只认官方来源——官方 changelog / release notes / 迁移指南 / 官方仓库的 tag 与 diff；② 博客、问答站、模型记忆、训练数据**不算依据**，只能用来定位线索，必须回到官方原文核对；③ 官方查不到的条目**显式写 `UNVERIFIED` + 查了什么 + 为什么给不出结论**——禁止含糊对冲：「应该没问题」「大概率兼容」一律不算结论。

**升级四查：**

**① 理由核实**：读官方 changelog / release notes / 安全通告，回执摘要（改了什么/破坏性变更有哪些/为什么本项目需要）。
❌ 反例："最新版性能更好"（没有数据、没有本项目的痛点对应）
✅ 正例："v3.2 修复了本项目正在用的 `parse()` 的内存泄漏（issue #123，我们的导出接口周报里出现过）"

**② 兼容性影响面**：
```powershell
$dep = 'requests'          # 本次要升的依赖名
Get-ChildItem -Path src, tests -Recurse -File | Select-String -Pattern $dep | Select-Object Path, LineNumber, Line
```
Expected：每个调用点一行，表头 `Path` / `LineNumber` / `Line`（本机实测 `Path` 是绝对路径）；命中 0 行 = 这个依赖没有任何调用点，升它之前先确认真要升。
列出全部调用点，对照 changelog 的 breaking changes 逐条判断"本项目受不受影响"。
❌ 反例：`grep -rn "<依赖名>" src`（bash 专用命令 + 占位符，Windows 上跑不动，还会漏掉 src 之外的调用点）
✅ 正例：上面那条 `Get-ChildItem -Path src, tests -Recurse -File | Select-String -Pattern $dep`（PowerShell 5.1 可跑，输出 Path/LineNumber/Line）
（注：本机 PowerShell 5.1 里 `-Recurse` 不是 `Select-String` 的合法形参，只有上面的管道式递归可跑）

**③ 准备升级改动（lockfile 与代码适配分开提交；提交动作放 §④，本段不提交）**：
```powershell
$dep = 'requests'; $old = '2.30.0'; $new = '2.31.0'
# 升级命令按 .tool-versions 的包管理器填，例：pnpm add requests@2.31.0 ／ pip install -U requests==2.31.0
$lock = 'pnpm-lock.yaml'          # lockfile 文件名按实际包管理器换
$adapter = 'src/export_limit.py'  # 本次代码适配文件，逐个列出
```
Expected：本段是赋值，不产出输出（空输出就是对的）；`$dep` / `$old` / `$new` 供 §④ 的提交信息复用，必须与本项目真实栈一致（占位值照抄 = 提交信息写错）。
- lockfile 单独一个提交（保住回滚粒度），代码适配另起一个提交
- 破坏性变更的适配必须写明"改前行为 → 改后行为"

**④ 全量验证**：`powershell -NoProfile -File check.ps1` 退出码 0 + 粘贴输出（在 §④ 提交后跑）。不过时按失败面二选一回滚（升级失败也是有效结论）：
```powershell
$lockCommit = 'abc1234'      # §④ 第一个提交（lockfile），跑完 git log --oneline -2 取
$adapterCommit = 'def5678'   # §④ 第二个提交（代码适配）
git revert $lockCommit       # 依赖本身不行 → 撤 lockfile（适配提交也应一并撤）
git revert $adapterCommit    # 依赖没问题、只是适配写错 → 只撤适配，保留升级
```
Expected：按失败面**只走一支** —— 撤销各产生一个 revert 提交（`git log --oneline -3` 里可见），撤回后重跑 `check.ps1` 取 0 才算回滚成立（升级失败也是有效结论）。
（一次 `git revert` 只处理一个提交；两个都要撤就依次执行两条，别把两个哈希塞进一条命令。）

**禁令：**
- 禁止在一次任务里升多个**大版本**（互相干扰没法定位）
- 禁止跳过 lockfile 单独提交（回滚粒度没了）
- 禁止把目标写成"升到最新版"（版本号必须具体）
- 破坏性大版本升级 → 不是本卡的事，立项走 L 档全流程

---

## ③ 证据回执

1. `STACK DETECTED` 行原文（工具 + 确切版本 + 来源命令）
2. 版本变化：依赖名 + 旧版本 → 新版本（具体号），动机归类
3. 兼容性结论：breaking changes 逐条"受/不受影响"+依据（依据必须是官方原文，标出出处；`UNVERIFIED` 条目逐条列出）
4. lockfile commit + 适配 commit 哈希（在 §④ 提交后回填）
5. `check.ps1` 输出 + 退出码

---

## ④ 状态回写

**顺序铁律：先回写状态 → 再提交 → 再复跑 check.ps1 取 0。**

更新 STATE.md：`当前任务` 清空；`下一步` = 5-1 归档；`.tool-versions` 若有版本行变化需同步更新并注明。

然后提交与复跑（提交信息里的 `$dep` / `$old` / `$new` 沿用 §③ 的赋值）：
```powershell
git add STATE.md .tool-versions $lock
git commit -m "7-2 chore(deps): bump $dep $old -> $new"
git add $adapter
git commit -m "7-2 fix(deps): adapt to $dep $new"
powershell -NoProfile -File check.ps1
```
Expected：两笔提交的提交信息逐字为 `7-2 chore(deps): bump <dep> <old> -> <new>`（lockfile 一笔）与 `7-2 fix(deps): adapt to <dep> <new>`（代码适配一笔；本次没有适配文件就跳过该笔并在回执写明）；`check.ps1` 退出码 0，非 0 = 升级失败，按 §④ 的回滚分支处置。

固定收尾语：
`等待你裁决。回复"继续"执行下一张卡，或说新指令。`
