> 触发：需要升级依赖（用户要求或安全补丁） ｜ 产物：升级提交 + 兼容性结论 ｜ 下一张：40 归档

## ① 开工确认

1. **升级动机三选一**（前两者才值得动手，"主动追新"要劝退）：
   - 安全补丁（有 CVE/漏洞通报）
   - 新功能需要（某个 Must 依赖新版本 API）
   - 主动追新（❌ 默认拒绝：没有收益只有回归风险）
2. **影响面预告**：将 grep 核对当前依赖被谁用。
3. **引用检查清单原文**（逐字粘贴"升级四查"）。

---

## ② 执行

**升级四查：**

**① 理由核实**：读官方 changelog / release notes / 安全通告，回执摘要（改了什么/破坏性变更有哪些/为什么本项目需要）。
❌ 反例："最新版性能更好"（没有数据、没有本项目的痛点对应）
✅ 正例："v3.2 修复了本项目正在用的 `parse()` 的内存泄漏（issue #123，我们的导出接口周报里出现过）"

**② 兼容性影响面**：
```powershell
grep -rn "<依赖名>" src
```
列出全部调用点，对照 changelog 的 breaking changes 逐条判断"本项目受不受影响"。

**③ 执行升级 + lockfile 单独提交**：
```powershell
<包管理器升级命令，按 .tool-versions 的包管理器>
git add <lockfile>
git commit -m "51 chore(deps): bump <依赖> <旧>-><新>"
git add <代码适配文件>
git commit -m "51 fix(deps): adapt to <依赖> <新版本>"
```

**④ 全量验证**：`powershell -File check.ps1` 退出码 0 + 粘贴输出。不过 → 回滚 lockfile 提交（`git revert`），升级失败也是有效结论。

**禁令：**
- 禁止在一次任务里升多个**大版本**（互相干扰没法定位）
- 禁止跳过 lockfile 单独提交（回滚粒度没了）
- 破坏性大版本升级 → 不是本卡的事，立项走 L 档全流程
