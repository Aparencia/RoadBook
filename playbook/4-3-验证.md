## ② 执行

**证据分档（先说清手里的证据算哪一档）：**

| 档 | 形态 | 谁来验 | 能不能算完成 |
| :-- | :-- | :-- | :-- |
| **A 档** | 命令执行输出（含退出码、测试输出、请求/响应 JSON、`Select-String` 结果） | 换个会话、换个人照贴的命令复跑一遍就能得到同样结果 | 可以 |
| **S 档** | 截图、录屏 | 人看得懂，但机器验不了 | 不可以 |

**声明"完成"至少要有 A 档证据；只有 S 档 = 未完成**（截图留作人工验收的辅助，不替代 A 档）。
**没有能变红的命令，就没有第二阶段**：任何判断若拿不出"它会因失败而变红"的命令，就只能进人工审核（写进行为验收清单），不许写成机器判据，也不许当成已验证——本卡后面的每一条判据先过这一关，过不了就降级为人工项。

**动作 1：跑收工仪式（guardrail）**

```powershell
powershell -NoProfile -File check.ps1
```

**完成的唯一合法定义：退出码 0 + 完整粘贴真实输出。**
其他一切"完成了/应该可以了"都不算完成。
❌ 反例："type-check 干净，所以验证通过"（type-check ≠ 验证）
✅ 正例：粘贴 check.ps1 的完整输出，末行"全部通过"，退出码 0
退出码不是 0 时分清两种：`2` = `$STEPS` 未配置（**环境未初始化，不是代码缺陷**，回 1-2 / 1-3 卡接 STEPS）；`1` = 真失败，逐条修。

**前置动作（先于任何命令）：先回答"哪个命令能证明这条主张"，再跑；写不出命令的主张不许说**（与 `AGENTS.md` §6 主张表配套）。例：主张"界面符合设计" → 命令 = 截图 + 取值；主张"数字改善" → 命令 = 同一条命令的前后两次数字。

**动作 2：按档位落地测试**
- M/L 档：写测试并跑通，粘贴测试输出。测试不许为凑通过而弱化断言。
  ❌ 反例：测试断言 `expect(result).toBeDefined()`（永远过的假测试）
  ✅ 正例：`expect(sum([1,2])).toBe(3)`，外加一个失败用例验证会报错
- **变异体证伪（"绿"要一问：判据真能被打红吗？）**——L 档每个测试判据、M 档每任务至少一次：临时改坏被测代码 → 测试必须变红 → 还原 → 复跑回绿。
  ❌ 反例：把 `amount * 0.9` 改成 `amount * 0.8`，测试仍然绿 = 这是"没牙的判据"（摆设），重写断言再证伪
  ✅ 正例：注入变异 → 具名判据变红 → 还原 → 复跑回绿 → 该判据有牙，证据成立
  **变异点至少覆盖三类**：① 常量或参数改错 ② 分支走错 ③ 缺状态变更或副作用（另两类：返回空/默认值、边界输入缺校验）——只把数字从 0.9 改成 0.8 不算覆盖。
  ⚠️ **变异体卫生**：读数诡异先怀疑运行器缓存（vitest 把缓存写进 node_modules，`--no-cache` 不够）——变异与复跑之间清缓存，或换临时副本目录跑（详见教训卡 `docs/lessons/<日期>_测量载体脱钩.md`）
- 发现自己在"改测试迁就代码"→ 立即停止并声明（这是作弊）。

**动作 2.5：场景走查（M/L 档；每条必须附证据——没贴输出/JSON/断言 = 没走过）**
agent 以真实运行状态逐情景走查，结果写进 VERIFY.md。情景菜单：
- □ 正常路径：SCOPE 验收标准逐条跑
- □ 空态/首次使用：无数据时打开各页面
- □ 边界数据：空输入/超长/0/负数/最大值/特殊字符
- □ 异常路径：后端报错时的表现/重复提交/断网
- □ 数据一致性：操作后核对存储的数据真的对（不只看界面显示）
- □ 回归：改动前可用的核心老功能仍可用
有浏览器能力走 UI 级（贴关键 DOM 断言/截图）；没有则走接口级 + 数据级（贴请求/响应 JSON、命令输出），点按钮那一层留给人工验收清单。

**动作 3：生成行为验收清单（3~5 条，给用户照着点）**
每条 = 打开哪页 → 做哪个动作 → 应看到什么。
❌ 反例："功能正常可用"
✅ 正例："打开本任务新增的入口页 → 点新增的『导出』按钮 → 2 秒内出现下载文件，导出条数与列表可见条数一致"——把 SCOPE 每条验收标准改写成这个句式，必须带可核对的数字或状态。
有 UI 的项目**清单第一条必须从现有界面入口出发**走到新功能（"从设置页点'导出'按钮 → 见下载文件"）——证明用户真的能到达它；禁止把"直接调 API 成功"当作功能完成的唯一证据（组件写好了但入口没装配，正是审查与验收最容易联手漏掉的事故）。纯后端给接口调用步骤（curl/PowerShell 可复制命令）。
清单写入 VERIFY.md（连同 check 输出与测试结果、场景走查表）。**VERIFY.md 末尾必须有「诚实边界」节：『本任务未验证 / 做不到的』逐条列出（一条没有也要写"无"），不得合并同类项、不得省略**——防"未判定"被写成"全绿"。

**动作 4：预检归档条件**
- 改过 UI/表/接口吗？提醒 5-1 卡要回写 registry（先自查一遍并回执）。

**禁令：**
- 禁止跳过 check.ps1 直接说"验证通过"
- 禁止无证据声称"走过某场景"（没贴输出/JSON/断言 = 没走）
- 禁止替用户宣布"验收通过"——你只能提交清单，验收是人做的事
- 禁止在验收清单里写用户做不到的操作（需要 SSH 的、需要看日志的都不算行为验收）
- 禁止在证据出现前表达满意（"太好了 / 完美 / 搞定 / 没问题"这类词先于输出出现 = 本轮判未验证）
- 禁止用"应该 / 大概 / 看起来"作为成功表述的修饰词（出现即按未验证处理）
